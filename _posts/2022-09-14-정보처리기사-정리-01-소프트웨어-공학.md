**1\. 소프트웨어 공학  : 소프트웨어 위기를 극복하고, 품질 높은 소프트웨어를 개발하기 위한 학문**

**2\. 소프트웨어 공학의 3R  : 완성된 소프트웨어를 기반으로 역공학, 재공학, 재사용을 통해 소프트웨어의 생산성을 극대화하는 방법**  
  
**1) 역공학 (Reverse Engineering) : 기존 개발된 시스템을 CASE 도그를 이용하여 사양서, 설계서 등의 문서로 추출하는 작업 (기 개발된 소프트웨어의 분석을 도와줌)**

**2) 재공학 (Re-engineering) : 기존 시스템을 널리 사용되는 프로그래밍 표준에 맞추어 고수준의 언어로 재구성하거나 이기종에서 사용할 수 있도록 변환하는 작업**

**3) 재사용(Reuse) : 이미 개발되어 그 기능, 성능 및 품질을 인정받았던 소프트웨어를 다시 사용**

**\*\* 재사용 방법 :**   
**3-1 ) 합성 중심 : 블록(모듈)을 만들어서 끼워 맞추어 소프트웨어를 완성시키는 방법**  
**3-2 ) 생성 중심 : 추상화 형태로 쓰여진 맹세를 구체화하여 프로그램을 만드는 방법**

**3\. 소프트웨어 개발 단계**  
**계획 -> 요구사항 분석 -> 설계 -> 구현 ->  테스트 -> 유지보수**  
  
**4\. 소프트웨어 개발 방법론 종류**  
**4-1) 구조적 방법론 (하향식) : 절차지향 소프트웨어 개발 방법론, 순차적 실행**   
**\*\* 구성요소 : 데이터 흐름도(DFD), 자료사전(DD), 상태전이도(STD), 소단위 명세서(Minespec)**  
**4-2) 정보공학 방법론 : 주로 기업에서 사용하는 방법론**  
**4-3) 객체지향 개발 방법론 (상향식) : 현실세계의 개체(Entity)를 속성(Attribute)과 메서드(Method) 형태로 표현, 객체중심 개발**  
**\*\* 특징 : 캡슐화, 정보은닉, 상속, 다형성, 추상화**

**4-4) CBD (Component Based Development) 분석 방법론 : 재사용 가능한 컴포넌트의 개발 또는 상용 컴포넌트를 조합해 어플리케이션 개발**  
**4-5) 애자일 방법론 : 절차를 중요시하게 여기게 되면서, 변화에 빠른 대응을 할 수 없는 단점 개선을 위한 방법론**  
**\*\* 종류 : XP(eXtreme Programming), SCRUM, FDD, Crystal**   
  

**5\. 소프트웨어 개발 모델**  
**5-1) 폭포수 모델 : 계획, 분석, 설계, 구현, 테스트, 전 과정을 순처작을 접근하는 모델**  
**\*\* 특징 : 요구사항 변경 어려움, 산출물이 명확**  
**5-2) 프로토타이핑 : 고객이 요구한 주요 기능을 프로토타입으로 구현하여 완성해가는 모델**  
**5-2) 나선형 모델 : 폭포수, 프로토타이핑의 장점을 수용, 위험분석을 추가한 점증적 개발 모델**  
**\*\* 순서 : 계획수립(planning) - 위험분석(Risk Analysis) - 공학적개발(Develpoment) - 평가(Evaluation)**  
**\*\* 특징:  위험성이 큰 프로젝트를 수행, 고객의 요구사항을 보다 더 상세히 적용, 시간과 비용이 많이 듦**  
**5-3) RAD (Rapid Application Development) 모델 : 매우 짧은 개발주기를 강조하는 점진적 개발 방식, 60~90일**  
**5-2) V 모형 : 폭포수 모델에 시스템 검증과 테스트 작업을 강조**  
**\*\* 특징 : 높은 신뢰성이 요구되는 분야에 적합**  
**\*\* 중요한 순서 : 단위 테스트 -> 통합 테스트 -> 시스템 테스트 -> 인수테스트**

**5-3) 4세대 기법 : CASE등의 자동화도구를 이용하여 요구사항 명세서로부터 원시코드 자동으로 생성**

**6\. 애자일(Agile) 방법론 종류**  
**6-1) XP (eXtreme Programming) : 문서보다는 코드를 중시, 5가지 핵심가치, 12개 실천 항목, 1~3주의 반복 개발**  
**\*\* 5 핵심가치**   
**\[1\] 용기 - 요구사항 변화에 능동적 대처**  
**\[2\] 존중 - 개발자 역량 존중**  
**\[3\] 피드백 - 의사소통에 따른 피드백**  
**\[4\] 의사소통 - 개발자, 관리자, 고객 간의 의사소통**  
**\[5\] 단순성 - 사용되지 않는 구조와 알고리즘 배제**  
  
**\*\* 12가지 실천 사항**  
**\[1\] 짝 프로그래밍 (Pair Programming) : 하나의 작업을 2명의 프로그래머가 수행**  
**\[2\] 계획 세우기 (Planning Game) : 게임처럼 규칙, 목표를 두고 기획 수행**

**\[3\] 테스트 기반 개발 (Test Driven Development) : 선 단위 테스트 후 코드 작성**  
**\[4\] 고객 상주 (Whole Team) : 고객이 프로젝트 팀원으로 상주**  
**\[5\] 지속적인 통합 (Continuous Intergration) : 상시 빌드 및 배포가 가능한 상태로 유지**  
**\[6\] 코드 개선 (Desing Improvement) : 리팩토링**  
**\[7\] 작은 릴리즈 (Small Releases) : 짧고 잦은 릴리즈로 고객이 변경사항을 볼 수 있도록 함**

**\[8\] 코딩 표준 (Coding Standards) : 표준화된 관례에 따라 코드 작성**

**\[9\] 공동 코드 소유 (Collective Code Ownership) : 시스템에 있는 코드는 팀의 모든 프로그래머가 수정 가능**  
**\[10\] 간단한 디자인 (Simple Design) : 간결한 디자인 상태 유지**  
**\[11\] 시스템 메타포어 (System Metaphor) : 최종적으로 개발 되어야 할 시스템 구조 조망**  
**\[12\] 작업시간 준수 (Sustainable Pace) : 주 40시간, 2주연속 오버타임 금지**  
  
**7\. 스크럼 (SCRUM) : 소프트웨어에 포함될 기능, 개선점에 대한 우선 순위 부여, 개발주기는 30일정도(스프린트)로 조절, 날마다 15분 정도 회의 진행**
