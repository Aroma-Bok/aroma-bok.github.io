### 들어가며

요즘 AI 글이나 발표에는 "AI Agent"와 "Agentic AI"가 거의 매번 나온다. 그런데 두 용어를 같은 뜻으로 쓰는 글도 있고, 다른 개념이라고 구분하는 글도 있어서 헷갈린다. 이 글은 **두 용어의 개념과 차이**를 먼저 정리하고, 그것이 **일하는 방식**을 어떻게 바꾸는지까지 이어서 정리한 것이다.

먼저 밝혀 둘 점이 있다. 두 용어에는 **공식 표준 정의가 없다.** 글마다 정의가 조금씩 달라서, 아래는 가장 흔하게 쓰이는 구분을 기준으로 했다.

### 1. 먼저 결론

- **AI Agent**는 LLM이 **도구를 호출하면서 목표를 향해 작업을 수행하는 하나의 단위(개체)** 다.
- **Agentic AI**는 에이전트들이 **스스로 계획하고, 역할을 나누고, 협업하며 움직이는 시스템 또는 그런 성질**이다. AI Agent보다 넓고 자율성이 높은 개념이다.
- Agentic은 "에이전트다운"이라는 **형용사**라서 `agentic 워크플로`, `agentic RAG`처럼 **성질**을 나타낼 때도 쓴다.
- 자율성은 이분법이 아니라 **스펙트럼**이다. 정해진 순서대로 실행하는 쪽에서 스스로 계획하는 쪽까지 단계가 있다.
- 일하는 방식으로 옮겨 보면, **사람은 실행보다 목표 정의, 검증, 책임에 더 집중**하게 된다.

### 2. AI Agent란

챗봇은 질문을 받아 **텍스트로 답하는 것**까지가 역할이다. AI Agent는 거기서 한 걸음 더 나가서 **행동**한다. 일정을 조회하고, 검색하고, API를 호출하고, 결과를 보고 다음 행동을 정한다.

구성 요소는 보통 네 가지로 설명한다.

- **LLM(두뇌)**: 상황을 이해하고 다음에 무엇을 할지 판단한다.
- **도구(Tool)**: 검색, DB 조회, 외부 API, 코드 실행처럼 LLM이 직접 할 수 없는 일을 대신해 주는 기능이다. LLM은 도구를 직접 실행하지 않고 "이 도구를 이 인자로 호출하라"는 요청을 만들고, 실제 실행은 애플리케이션이 한다.
- **메모리**: 지금까지의 대화와 중간 결과를 기억한다. 한 번의 작업 안에서 쓰는 단기 기억과, 작업을 넘어 쌓아 두는 장기 기억(보통 벡터 DB 등)으로 나눈다.
- **계획(Planning)**: 큰 일을 작은 단계로 나누고, 결과를 보고 방향을 고친다.

동작은 대체로 **관찰 → 판단 → 행동**을 목표가 달성될 때까지 반복하는 루프다. 널리 알려진 ReAct 방식이 대표적이다. 생각(Reason)하고 행동(Act)한 뒤, 그 결과를 관찰해서 다시 생각하는 것을 반복한다.

```text
목표 → [생각: 무엇이 필요하지?] → [행동: 검색 도구 호출] → [관찰: 결과 확인]
         ↑                                                        │
         └──────────── 부족하면 다시 ──────────────────────────────┘
                                   충분하면 → 최종 답변
```

예를 들면 `고객 문의에 답하는 봇`, `메일을 요약하고 일정을 잡아 주는 봇`처럼 **비교적 범위가 정해진 작업 하나**를 맡는 것이 전형적인 AI Agent다.

### 3. Agentic AI란

Agentic AI는 이 에이전트를 **여러 개, 더 큰 목표에 맞춰 엮은 것**을 가리킬 때 쓰는 경우가 많다. 목표만 주면 다음과 같은 일을 시스템이 알아서 한다.

- 큰 목표를 **하위 작업으로 쪼개고**
- 작업별로 **전문 에이전트에게 나눠 맡기고**
- 중간 결과를 **합치고 검토하고**
- 틀렸거나 부족하면 **계획을 고쳐서 다시 시도**한다.

예를 들어 "경쟁사 시장 조사 보고서를 만들어 줘"라는 목표가 주어졌다고 하자. 자료 수집 에이전트, 분석 에이전트, 작성 에이전트, 검토 에이전트가 역할을 나눠서 움직이고, 이를 조율하는 오케스트레이터가 흐름을 관리하는 식이다.

비유하면 이렇다.

- **AI Agent**는 일 잘하는 **직원 한 명**이다. 시키면 도구를 써서 해 온다.
- **Agentic AI**는 프로젝트를 맡은 **팀**이다. 목표를 주면 팀장이 계획하고, 담당을 나누고, 결과를 합치고, 부족하면 다시 돌린다.

### 4. 한눈에 비교

| | AI Agent | Agentic AI |
|---|---|---|
| 범위 | 좁음. 특정 작업 하나 | 넓음. 복잡한 목표 전체 |
| 구성 | LLM + 도구 + 메모리 (단일 단위) | 여러 에이전트 + 오케스트레이션 + 공유 메모리 |
| 목표 | 사람이 정해 준 작업을 수행 | 큰 목표를 스스로 하위 작업으로 분해 |
| 자율성 | 정해진 범위 안에서 | 계획 수립, 재시도, 방향 수정까지 |
| 협업 | 보통 단독 | 에이전트 간 역할 분담과 협업 |
| 예시 | 메일 요약 봇, 일정 예약 봇 | 조사 → 분석 → 작성 → 검토를 여러 에이전트가 처리 |

경계는 모호하다. 같은 시스템을 어떤 글은 AI Agent라고, 어떤 글은 Agentic AI라고 부른다. 글이나 발표를 볼 때는 용어보다 **"단일 에이전트 이야기인가, 여러 에이전트와 계획 단계까지 포함한 이야기인가"** 를 먼저 보면 이해가 쉽다.

### 5. 워크플로 vs 에이전트: 자율성은 스펙트럼

"에이전트를 만든다"고 할 때 가장 중요한 구분은 **누가 흐름을 정하는가**다. Anthropic의 에이전트 설계 글에서도 이 둘을 구분한다.

- **워크플로(Workflow)**: 사람이 **미리 정한 경로**를 따라 LLM과 도구가 실행된다. 흐름은 코드나 캔버스에 고정되어 있고, LLM은 각 단계에서 일을 수행한다.
- **에이전트(Agent)**: **LLM이 스스로 흐름과 도구 사용을 결정**한다. 다음에 무엇을 할지, 언제 끝낼지를 LLM이 판단한다.

이 구분에서 **agentic system(에이전틱 시스템)** 은 워크플로와 에이전트를 **모두 아우르는 상위 용어**다. 정리하면 다음과 같다.

```text
agentic system (LLM이 도구를 쓰며 일하는 시스템 전체)
 ├─ 워크플로: 경로를 사람이 정함  → 엄밀한 의미에서는 AI Agent가 아님
 └─ 에이전트: 경로를 LLM이 정함   → AI Agent
```

- 이 용법에서는 워크플로는 AI Agent가 **아니고**, 에이전트만 AI Agent다.
- 다만 제품 설명이나 발표에서는 워크플로형 시스템도 느슨하게 "AI Agent"라고 부르는 경우가 많다. 이 글의 앞부분에서 쓴 `Agentic AI = 여러 에이전트가 협업하는 시스템`이라는 설명도 그런 흔한 용법 중 하나이고, 위의 "상위 용어" 용법과는 결이 다르다. 같은 단어가 글마다 다르게 쓰이므로, 읽을 때 **어떤 의미로 쓴 글인지** 확인하는 것이 좋다.

실제로는 이 둘 사이에 단계가 있다.

| 단계 | 흐름을 정하는 쪽 | 설명 |
|---|---|---|
| 1. 단일 LLM 호출 | 사람 | 질문 하나에 답 하나 |
| 2. 고정 워크플로 | 사람 | 질문 이해 → 검색 → 생성처럼 순서가 정해져 있음 |
| 3. 분기가 있는 워크플로 | 사람이 정한 조건 + LLM의 분류 | LLM이 질문을 분류하면 정해진 경로로 갈라짐 |
| 4. 에이전트 | LLM | LLM이 도구를 골라 쓰고 반복하며 끝낼 때를 정함 |
| 5. 멀티 에이전트 | 오케스트레이터 + 각 에이전트 | 목표를 쪼개 여러 에이전트에 분담 (Agentic AI) |

자주 쓰는 워크플로 패턴은 다음과 같다.

- **프롬프트 체이닝**: 단계를 순서대로 잇는다. 앞 단계의 출력이 다음 단계의 입력이 된다.
- **라우팅**: 입력을 분류해서 알맞은 처리 경로로 보낸다. (환불 문의 → 환불 담당, 배송 문의 → 배송 담당)
- **병렬화**: 독립적인 작업을 동시에 실행하고 결과를 합친다.
- **오케스트레이터-워커**: 중앙 LLM이 작업을 쪼개 워커에게 나누고 결과를 종합한다.
- **평가자-최적화**: 한쪽이 결과를 만들고 다른 쪽이 평가해서, 기준을 넘을 때까지 반복한다.

**더 자율적이라고 더 좋은 것은 아니다.** 자율성이 높아질수록 얻는 것과 잃는 것이 같이 늘어난다.

- 얻는 것: 정해 두지 못한 상황에도 대응하고, 복잡한 일을 스스로 풀 수 있다.
- 잃는 것: 결과를 **예측하기 어렵고**, 비용(호출 횟수)이 커지고, **오류가 단계를 거치며 쌓이거나 번질 수 있다.** 디버깅도 어려워진다.

그래서 현장에서는 **흐름이 예측 가능한 일은 워크플로로, 경로를 미리 정할 수 없는 일만 에이전트로** 푸는 것이 권장된다. 단순한 구조로 시작해서 필요할 때만 자율성을 늘리는 편이 안전하다.

### 6. 실제 제품으로 보기: RAG 플로우형 vs 자율 에이전트형

용어가 추상적이라서, 실제 제품 유형으로 옮겨 보면 이해가 쉽다. 에이전트를 다루는 제품은 크게 두 갈래로 나뉜다.

- **RAG 플로우형(워크플로형)**: 캔버스에서 노드를 연결해 질문 이해, 검색, 도구 호출, 생성, 답변 흐름을 조립한다. **정해진 절차를 빠르고 정확하게** 실행하는 것이 목적이다.
- **자율 에이전트형**: 목표를 받고 **단계별로 추론하며 목표까지** 스스로 나아간다. 어떤 도구를 어떤 순서로 쓸지는 LLM이 실행 중에 정한다.

| | RAG 플로우형 | 자율 에이전트형 |
|---|---|---|
| 분류 | **워크플로** | **에이전트** (엄밀한 의미의 AI Agent) |
| 행동 방법 | 사전에 정해 둔 절차대로 실행 | 상황을 보고 그때그때 정함 |
| 행동을 정하는 시점 | 설계할 때 (사람) | 실행 중에 (LLM) |
| 강점 | 빠르고 정확하고 결과가 예측됨 | 경로를 미리 못 그리는 일에 대응 |
| 약점 | 설계하지 않은 상황에 약함 | 예측이 어렵고 비용·지연이 크며 오류가 번질 수 있음 |
| 비유 | 매뉴얼을 따르는 직원 | 목표만 받고 알아서 판단하는 직원 |

두 유형의 차이는 **행동 방법**, 즉 **누가 언제 행동 순서를 정하는가**에 있다. 사용하는 LLM, 검색, 도구가 같아도 여기서 갈린다. 예측 가능성, 속도, 비용, 대응 범위 같은 성질은 이 차이에서 따라 나온다.

#### RAG 플로우에도 LLM이 있는데 왜 에이전트가 아닐까

플로우형에도 LLM은 핵심 역할을 한다. 질문을 재작성하고, 질문을 분류하고, 검색 결과로 답변을 생성한다. 하지만 **LLM의 유무가 기준이 아니다.** 기준은 LLM이 **무엇을 결정하느냐**다.

- **플로우형의 LLM**은 사람이 그려 둔 경로 안에서 **자기 칸의 일을 수행**한다. 분류 노드에서 갈래를 고르더라도 **갈 수 있는 길은 사람이 미리 정해 둔 후보**이고, 그중 하나를 고를 뿐이다. (라우팅 패턴이라 워크플로 범위다.)
- **에이전트의 LLM**은 **다음에 무엇을 할지, 어떤 도구를 쓸지, 언제 끝낼지**까지 정한다.

한 줄로 줄이면 **LLM이 칸을 채우면 워크플로, LLM이 칸을 만들면 에이전트**다.

#### 노코드 빌더 플랫폼의 위치

- **플랫폼 자체**는 에이전트가 아니라 워크플로를 만들고 **돌려 주는 빌더·실행 환경(하네스)** 에 가깝다.
- 그 위에서 만든 **파이프라인 하나**는 엄밀한 기준으로는 **워크플로**다. 느슨한 용법으로는 "AI Agent"라고 부르기도 한다.
- 파이프라인이 **다른 파이프라인을 호출**하도록 엮으면(분류 결과에 따라 전용 하위 파이프라인으로 보내는 식) 라우팅과 오케스트레이션이 들어간 **agentic한 구성**에 가까워진다. 그래도 경로는 사람이 정해 둔 것이라 워크플로의 범위 안이다.
- 스펙트럼으로는 3단계(분기가 있는 워크플로) 근처이고, 자율 에이전트형은 4단계다.
- "연결(오케스트레이션)은 플랫폼이 하고, 판단은 노드 안의 LLM이 한다"고 보면 이해가 쉽다. 노코드라는 말은 **연결에 코드가 필요 없다**는 뜻이지, 연결 대상(조회 API 같은 업무 로직)을 대신 만들어 준다는 뜻은 아니다. 그건 따로 있어야 한다.

#### 무엇을 고를까

- 질문 유형과 처리 절차가 정해져 있고 **정확성, 속도, 재현성**이 중요하면 → **플로우형(워크플로)**
- 목표는 있지만 **경로를 미리 그릴 수 없는** 복잡하고 열린 문제면 → **자율 에이전트형**
- 둘은 우열이 아니라 **용도가 다른 도구**다. 앞서 말한 대로 단순한 구조로 시작하고, 필요할 때만 자율성을 늘리는 편이 안전하다.

### 7. 일하는 방식은 어떻게 달라질까

에이전트가 일을 맡기 시작하면 사람의 일이 이렇게 이동한다.

#### 실행에서 설계와 위임으로

- 예전에는 사람이 **직접 해서** 결과를 만들었다면, 이제는 **무엇을 어디까지 맡길지** 정하는 일이 중요해진다.
- 좋은 위임은 목표, 제약(하면 안 되는 것), 완료 기준, 쓸 수 있는 도구를 명확히 주는 것이다. 사람에게 일을 시킬 때와 같다. 애매하게 맡기면 애매한 결과가 돌아온다.

#### 만드는 일에서 검증하는 일로

- AI는 틀릴 수 있고, 틀린 결과도 **그럴듯하게** 내놓는다. 그래서 결과를 그대로 쓰지 않고 **근거를 확인하고 판단**하는 일이 늘어난다.
- 검증하려면 **도메인 지식**이 있어야 한다. 모르는 분야의 결과는 틀려도 알아챌 수 없다.
- 그래서 AI를 쓸수록 **기초 지식의 가치는 오히려 올라간다.**

#### 사람의 개입 지점을 설계하기: human-in-the-loop

- 모든 걸 자동으로 돌리기보다, **어느 지점에서 사람이 확인할지**를 정해 둔다. 결제, 삭제, 외부 발송처럼 되돌리기 어려운 행동 앞에는 사람의 승인을 두는 것이 기본이다.
- 현장에서는 대체로 **AI가 초안과 1차 처리를 하고, 사람이 검토와 최종 판단**을 하는 협업 구조로 설계된다.
- 자율성을 한 번에 주지 않고, **믿을 수 있다고 확인된 범위부터 점차 넓힌다.**

#### 일을 "단계와 입출력"으로 바라보기

- 에이전트를 설계하려면 내 일을 **단계로 쪼개고, 각 단계의 입력과 출력을 정의**할 수 있어야 한다.
- 이 습관은 자동화, 문서화, 협업 모두에 도움이 된다. 일이 머릿속에만 있으면 AI에게도 사람에게도 맡길 수 없다.

#### 책임은 사람에게 남는다

- 결과물을 AI가 만들었더라도 **내보내는 사람이 책임**진다. "AI가 그랬다"는 말은 통하지 않는다.
- 그래서 **기록(로그, 추적)** 이 중요하다. 어떤 입력에서 어떤 도구를 호출해 어떤 결과가 나왔는지 나중에 확인할 수 있어야 틀렸을 때 고칠 수 있다.
- 민감 정보를 넣어도 되는지, 권한 범위를 넘지 않는지 같은 **보안과 윤리 감각**도 필요하다.

#### 일 잘하는 사람의 모습이 달라진다

| | 이전 | AI 에이전트 시대 |
|---|---|---|
| 핵심 가치 | 직접 빠르게 처리하는 능력 | 무엇을 할지 정하고, 맞는지 판단하는 능력 |
| 일의 단위 | 내가 하는 작업 | 에이전트에게 맡길 수 있는 작업 단위 |
| 결과물 | 내가 만든 것 | 검토하고 책임지는 것 |
| 학습 | 한 번 배우면 오래 쓴다 | 도구가 계속 바뀌어서 계속 실험한다 |

### 8. 흔한 오해

- **"에이전트면 무조건 자율적이다"**: 실제 사용되는 에이전트 상당수는 사람이 흐름을 정해 둔 워크플로에 가깝다. 이는 결함이 아니라 예측 가능성을 위한 선택이다.
- **"Agentic AI가 AI Agent보다 항상 낫다"**: 더 복잡할 뿐이다. 비용, 지연, 오류 위험도 같이 커서, 문제에 맞는 수준을 골라야 한다.
- **"에이전트를 도입하면 사람이 필요 없다"**: 오히려 검증과 책임, 설계 역할이 더 중요해진다.
- **"LLM이 들어 있으면 에이전트다"**: LLM의 유무가 아니라 **LLM이 행동 순서를 정하는가**가 기준이다. 정해진 절차 안에서 LLM이 각 단계를 수행하는 것은 워크플로다.
- **"챗봇에 도구 하나 붙이면 에이전트다"**: 도구를 쓰는 것만으로는 부족하고, 결과를 보고 **다음 행동을 스스로 판단하는 루프**가 있어야 에이전트에 가깝다.

### 정리

- **AI Agent**는 LLM이 도구를 쓰며 작업을 수행하는 단위이고, **Agentic AI**는 여러 에이전트가 계획하고 협업하는 시스템이나 성질이다. 정의는 글마다 조금씩 다르다.
- 구분의 핵심은 **누가 흐름을 정하는가**다. 사람이 정하면 워크플로, LLM이 정하면 에이전트에 가깝고, 그 사이는 스펙트럼이다.
- 실제 제품으로 보면 **RAG 플로우형은 워크플로**(절차를 사람이 정함), **자율 에이전트형은 에이전트**(절차를 LLM이 정함)다. 차이는 LLM의 유무가 아니라 **행동 방법, 즉 누가 언제 행동 순서를 정하는가**다.
- 자율성이 높을수록 유연해지지만 예측 가능성은 떨어지고 비용과 오류 위험은 커진다. **단순한 구조로 시작해서 필요할 때만 늘리는 것**이 안전하다.
- 일하는 방식은 **실행 중심에서 설계, 위임, 검증, 책임 중심으로** 이동한다. 사람이 확인할 지점을 설계하고, 결과를 검증할 도메인 지식을 갖추는 것이 중요해진다.
