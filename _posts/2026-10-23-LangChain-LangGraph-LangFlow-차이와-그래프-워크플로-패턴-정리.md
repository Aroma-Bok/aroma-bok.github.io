### 들어가며

노코드·로우코드 에이전트 빌더로 복잡한 흐름을 만들어야 하는데, 참고할 사례가 부족하다는 이야기를 들었다. 그러면 **LangGraph, LangFlow의 Best Practice에서 비슷한 사례를 찾아보라**는 조언을 받았다. 문제는 세 이름(LangChain, LangGraph, LangFlow)이 너무 비슷해서 무엇이 무엇인지부터 헷갈린다는 것이다. 먼저 셋의 차이를 정리하고, 그다음 "그래프로 흐름을 짠다"는 게 무슨 뜻인지, 어떤 패턴을 참고하면 되는지 정리해본다.

### 1. 한 줄 비교

| 이름 | 한 줄 정의 | 만드는 방식 |
|---|---|---|
| **LangChain** | LLM 앱을 만들 때 쓰는 **부품 모음 라이브러리** | 코드 |
| **LangGraph** | LangChain 계열의 **복잡한 흐름(분기·반복) 전용 라이브러리** | 코드 |
| **LangFlow** | 컴포넌트를 **화면에서 선으로 연결**해 흐름을 만드는 시각 빌더 | 화면(로우코드) |

- **LangChain**: 모델 호출, 프롬프트 템플릿, 검색, 도구 호출 같은 **부품**을 제공한다
- **LangGraph**: 그 부품들을 **노드와 선(엣지)으로 엮어** 상태를 가진 흐름을 만든다
- **LangFlow**: 같은 종류의 부품을 **코드 없이 캔버스에서** 배치하고 연결한다

### 2. LangChain - 부품 모음

LLM 앱은 대체로 "프롬프트 만들기 → 모델 호출 → 결과 가공" 같은 반복되는 조각으로 이뤄진다. LangChain은 이 조각을 **미리 만들어둔 부품**으로 제공해서, 매번 직접 짜지 않게 해준다.

- **모델 연결**: 여러 LLM 제공사를 같은 방식으로 호출
- **프롬프트 템플릿**: 변수를 끼워 넣는 프롬프트
- **검색(Retriever)**: 벡터DB 등에서 관련 문서를 찾아오는 부품
- **도구(Tool)**: 모델이 호출할 수 있는 함수

주로 **위에서 아래로 한 방향으로 흐르는 체인**을 만들 때 편하다. 다만 "검사에 실패하면 다시 쓰기" 같은 **되돌아가는 흐름**은 표현하기가 불편해진다.

### 3. LangGraph - 흐름을 그래프로

LangGraph는 되돌아가는 흐름을 자연스럽게 만들려고 나온 도구다. 핵심 개념은 네 가지다.

- **상태(State)**: 흐름 전체가 공유하는 데이터 (질문, 초안, 검사 결과, 시도 횟수 등)
- **노드(Node)**: 상태를 받아서 일부를 바꿔 돌려주는 **하나의 작업** (LLM 호출, 코드 검사 등)
- **엣지(Edge)**: 노드 사이의 **연결선**
- **조건부 엣지**: 상태를 보고 **다음에 갈 노드를 고르는** 선 (분기, 반복의 핵심)

작은 예를 보자. "초안을 쓰고 → 검사하고 → 통과하면 끝, 실패하면 다시 쓴다(최대 2번)"는 흐름이다.

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    draft: str
    ok: bool
    tries: int

def write(state: State):
    # 실제로는 LLM 호출
    return {"draft": "초안", "tries": state["tries"] + 1}

def check(state: State):
    # 실제로는 코드 검사나 LLM 검사
    return {"ok": False}

def route(state: State):
    return "done" if state["ok"] or state["tries"] >= 2 else "retry"

g = StateGraph(State)
g.add_node("write", write)
g.add_node("check", check)
g.add_edge(START, "write")
g.add_edge("write", "check")
g.add_conditional_edges("check", route, {"done": END, "retry": "write"})

app = g.compile()
app.invoke({"question": "...", "draft": "", "ok": False, "tries": 0})
```

핵심은 마지막 줄 위의 `add_conditional_edges`다. 검사 노드 뒤에서 **상태를 보고 끝낼지 다시 쓸지를 고른다.** 반복 횟수 상한(`tries >= 2`)을 두지 않으면 무한 반복이 될 수 있어서, **반복 흐름에는 항상 종료 조건을 같이 둔다.**

### 4. LangFlow - 화면에서 연결하는 빌더

LangFlow는 위와 같은 흐름을 **코드 대신 캔버스에서** 만든다. 입력, 프롬프트, 모델, 검색, 출력 같은 **컴포넌트 상자를 놓고 선으로 연결**하면 된다. 코드를 모르는 사람도 구조를 보고 이해할 수 있고, 빠르게 실험하기 좋다.

대신 도구마다 **지원하는 컴포넌트와 제어 방식이 달라서**, 코드로 만들 수 있는 흐름이 화면에서는 그대로 안 될 수 있다. 이 부분은 쓰려는 도구에서 직접 확인해야 한다.

### 5. 같은 "그래프"인데 왜 참고가 될까

세 도구와 노코드 에이전트 빌더는 모두 **"작업(노드)을 선으로 연결해 흐름을 만든다"**는 같은 기본 개념을 쓴다. 그래서 어떤 도구에서든 **"이 로직은 그래프로 이렇게 짠다"**는 패턴은 그대로 배울 수 있다.

참고할 때는 다음 순서가 편하다.

1. **입력과 출력을 먼저 정의**한다
2. **시나리오를 단계별로 논리적으로 설계**한다 (종이에 상자와 화살표로 그려본다)
3. 같은 구조를 **LangChain·LangGraph에서는 어떻게 구성하는지** 찾아본다
4. 그 구조를 **내가 쓰는 도구에서 구현할 수 있는지** 확인한다

### 6. 자주 나오는 그래프 패턴

복잡해 보이는 흐름도 대부분 아래 몇 가지 패턴의 조합이다. (LangGraph 문서와 에이전트 설계 글에서 자주 소개되는 패턴을 내 식으로 정리했다.)

| 패턴 | 하는 일 | 예 |
|---|---|---|
| **순차 체인** | 단계를 차례대로 실행 | 조건 정리 → 검색 → 작성 → 형식 점검 |
| **라우팅(분기)** | 입력 종류에 따라 다른 경로로 보냄 | 유형별로 다른 프롬프트 사용 |
| **병렬화** | 독립적인 작업을 동시에 실행하고 결과를 합침 | 여러 검증 항목을 동시에 검사 |
| **평가-개선 루프** | 결과를 평가하고 기준 미달이면 다시 생성 | 검사 실패 시 수정 후 재검증, 횟수 상한 |
| **오케스트레이터-워커** | 큰 작업을 쪼개 여러 워커에 맡기고 취합 | 문서를 나눠서 각각 요약 후 합치기 |
| **사람 개입(HITL)** | 중간에 사람이 승인·수정 | 최종 결과를 담당자가 확인 후 확정 |

처음에는 **순차 체인 → 라우팅 → 평가-개선 루프** 순으로 익히면 대부분의 시나리오가 설명된다.

### 7. 도구를 고르는 기준

| 상황 | 어울리는 것 |
|---|---|
| 한 방향 흐름의 간단한 LLM 앱을 코드로 만들고 싶다 | LangChain |
| 분기·반복·상태 관리가 필요한 복잡한 흐름을 코드로 만들고 싶다 | LangGraph |
| 코드 없이 빠르게 구조를 만들고 눈으로 확인하고 싶다 | LangFlow 같은 시각 빌더 |

### 마무리

정리하면 **LangChain은 부품, LangGraph는 그 부품을 엮는 그래프, LangFlow는 그걸 화면에서 하는 도구**다. 그래프 기반 도구는 기본 개념이 비슷해서, 한 곳에서 본 패턴을 다른 곳에 가져다 쓸 수 있다. 복잡한 흐름을 설계해야 할 때는 도구 사용법부터 보기보다 **입력과 출력을 정의하고, 위 패턴 중 무엇을 조합할지 먼저 그려보는 것**이 시작점이다.
