### 들어가며

RAG 시스템 구조도를 보면 "원본은 S3, 메타데이터는 PostgreSQL, 검색용은 Vector DB" 같은 말이 한 줄에 같이 나온다. 그런데 **S3는 DB가 아니고**, **벡터 DB는 PostgreSQL로도 만들 수 있다.** 헷갈리던 저장소 종류를 한 번에 정리해본다.

### 1\. 큰 그림 - DBMS와 스토리지는 다르다

```
데이터 저장소
├─ DBMS (데이터베이스 관리 시스템): 데이터를 구조화해서 조회·검색·트랜잭션 관리
│   ├─ 관계형 (RDBMS)        : PostgreSQL, Oracle, MySQL, Tibero, CUBRID
│   └─ 비관계형 (NoSQL)
│       ├─ 문서형             : MongoDB
│       ├─ 키-값형            : Redis
│       ├─ 와이드 컬럼형      : Cassandra, HBase
│       ├─ 그래프형           : Neo4j
│       ├─ 검색엔진형         : Elasticsearch, OpenSearch
│       ├─ 시계열형           : InfluxDB, TimescaleDB
│       └─ 벡터형 (Vector DB) : Milvus, Qdrant, Weaviate, Pinecone
└─ 스토리지 (DBMS 아님): 데이터를 "파일/블록" 단위로 보관
    ├─ 블록 스토리지     : 서버 디스크, 클라우드 볼륨
    ├─ 파일 스토리지     : NAS, NFS
    └─ 오브젝트 스토리지 : AWS S3, MinIO
```

-   **DBMS**: 데이터 **안의 값**을 기준으로 찾고, 고치고, 합치고(JOIN), 동시에 여러 명이 써도 일관성을 지켜준다
-   **스토리지**: 데이터를 **통째로** 넣고 꺼낸다. 안의 내용을 질의하는 기능은 없다

### 2\. 관계형 DB (RDBMS)

표(테이블) 형태로 데이터를 저장하고 **SQL**로 다루는 가장 전통적인 DB다.

-   **스키마**: 테이블 구조(컬럼, 타입)를 미리 정해두고 그대로만 저장
-   **JOIN**: 여러 테이블을 키로 연결해서 조회
-   **트랜잭션(ACID)**: 여러 작업을 하나로 묶어 "전부 성공 아니면 전부 취소"를 보장
-   **강점**: 정합성이 중요한 업무 데이터(회원, 주문, 권한, 이력)
-   **약점**: 구조가 자주 바뀌거나, 비정형 데이터가 많거나, 초대규모로 수평 확장해야 할 때 부담

### 3\. NoSQL - "SQL만 있는 게 아니다"

NoSQL은 하나의 제품이 아니라 **관계형이 아닌 DB들을 묶어 부르는 말**이다. 각자 잘하는 일이 다르다.

| 종류 | 저장 방식 | 잘하는 일 | 대표 제품 |
|---|---|---|---|
| **문서형** | JSON 같은 문서 단위 | 구조가 유연한 데이터 | MongoDB |
| **키-값형** | 키 하나에 값 하나 | 초고속 조회, 캐시, 세션 | Redis |
| **와이드 컬럼형** | 행마다 컬럼이 달라도 됨 | 대용량 쓰기, 분산 저장 | Cassandra |
| **그래프형** | 노드와 관계(엣지) | 관계망 탐색 (추천, 지식 그래프) | Neo4j |
| **검색엔진형** | 역색인 | 키워드 전문 검색, 로그 분석 | Elasticsearch, OpenSearch |
| **시계열형** | 시간 순 데이터 | 모니터링 지표, 센서 데이터 | InfluxDB |
| **벡터형** | 숫자 벡터 | 의미 유사도 검색 (RAG) | Milvus, Qdrant |

-   RDBMS가 정합성(ACID)을 최우선으로 한다면, 많은 NoSQL은 **확장성과 속도**를 위해 일부를 양보한다
-   요즘은 경계가 흐려져서, RDBMS가 JSON·전문검색·벡터를 지원하고 NoSQL이 트랜잭션을 지원하기도 한다

### 4\. 벡터 DB

#### 무엇을 저장하나

임베딩 모델이 문장·이미지를 **의미가 담긴 숫자 배열(벡터)**로 바꾸면, 그 벡터를 저장하고 검색하는 DB다. 임베딩 자체는 [임베딩 모델 글](/posts/임베딩-모델이란-RAG-검색이-실제로-비교하는-것/)에 정리해뒀다.

#### 일반 DB와 검색 방식이 다르다

-   **일반 DB**: "값이 **같은** 것" → `WHERE name = '홍길동'`
-   **벡터 DB**: "의미가 **가까운** 것" → 질문 벡터와 거리가 가까운 상위 k개

거리를 재는 방법은 주로 세 가지다.

-   **코사인 유사도**: 방향이 얼마나 비슷한지 (텍스트 임베딩에서 가장 흔함)
-   **유클리드 거리(L2)**: 직선 거리
-   **내적(Dot Product)**: 크기와 방향을 함께 반영

#### 왜 전용 기술이 필요한가 - ANN

벡터 수백만 개와 하나하나 거리를 재면 너무 느리다. 그래서 **약간의 정확도를 양보하고 아주 빠르게 근사치를 찾는 ANN(Approximate Nearest Neighbor)** 인덱스를 쓴다.

-   **HNSW**: 그래프 형태로 이웃을 연결해두고 타고 내려가며 찾음. 빠르고 정확도 높음, 메모리 많이 씀
-   **IVF (IVFFlat 등)**: 벡터를 군집으로 나눠두고 가까운 군집 안에서만 찾음. 메모리 절약

#### 메타데이터 필터가 실무에서 중요하다

실제 서비스에서는 "의미가 비슷한 것" 중에서도 **"내가 볼 권한이 있는 것만"**, **"2024년 이후 문서만"** 같은 조건이 붙는다. 그래서 벡터 DB를 고를 때는 **메타데이터 필터를 얼마나 잘 지원하는지**가 검색 속도만큼 중요하다.

### 5\. PostgreSQL도 벡터 DB가 된다 - pgvector

PostgreSQL에 **`pgvector` 확장**을 설치하면 일반 테이블에 벡터 컬럼을 두고 유사도 검색을 할 수 있다.

```sql
CREATE EXTENSION vector;

CREATE TABLE document (
  id        bigserial PRIMARY KEY,
  title     text,
  owner_dept text,
  embedding vector(1024)
);

-- HNSW 인덱스 (코사인 거리)
CREATE INDEX ON document USING hnsw (embedding vector_cosine_ops);

-- 권한 조건 + 의미 검색을 SQL 한 번에
SELECT id, title
FROM document
WHERE owner_dept = 'HR'
ORDER BY embedding <=> '[0.12, -0.03, ...]'
LIMIT 5;
```

-   `<=>` 코사인 거리, `<->` 유클리드 거리, `<#>` 내적(음수값)
-   정확히는 **관계형 DB에 벡터 검색 기능을 덧붙인 것**이다

#### 전용 벡터 DB와 비교

| | PostgreSQL + pgvector | 전용 벡터 DB (Milvus, Qdrant 등) |
|---|---|---|
| 장점 | 메타데이터·권한·벡터를 **한 DB에서 SQL로** 처리. 백업·트랜잭션·운영 방식 그대로. 시스템이 하나 줄어듦 | 초대규모에서 검색 속도·확장성 유리. 벡터 전용 기능이 풍부 |
| 단점 | 데이터가 아주 커지면 튜닝 부담 | 운영할 시스템이 늘어남. 메타데이터를 따로 동기화해야 할 수 있음 |
| 어울리는 경우 | 이미 PostgreSQL을 쓰고, 규모가 중간 이하 | 벡터가 매우 많고 검색 트래픽이 큼 |

(규모 기준은 데이터·하드웨어에 따라 달라서 일반적인 경향으로만 보자)

OpenSearch·Elasticsearch도 벡터 검색을 지원해서, **키워드 검색(BM25)과 벡터 검색을 한 엔진에서 섞는 하이브리드 검색**에 많이 쓰인다.

### 6\. 스토리지 3종류

| 종류 | 저장 단위 | 접근 방식 | 주 용도 |
|---|---|---|---|
| **블록 스토리지** | 고정 크기 블록 | OS가 디스크처럼 마운트 | DB 데이터 파일, 서버 OS 디스크 |
| **파일 스토리지** | 폴더/파일 계층 | 경로로 접근 (NFS, SMB) | 공유 폴더, NAS |
| **오브젝트 스토리지** | 파일 + 메타데이터 + 키 | HTTP API (S3 API) | 대용량 원본 파일, 백업, 이미지·영상 |

-   **DB도 결국 블록 스토리지 위에서 돈다**: DBMS가 디스크 위에 자기 방식으로 파일을 관리하는 것
-   **S3는 제품명이지만 오브젝트 스토리지의 대명사**처럼 쓰인다. S3 API 호환 제품이 많아서, 설치형으로는 MinIO가 대표적이다 → [MinIO 정리 글](/posts/MinIO란-무엇인가-오브젝트-스토리지-기본-개념-정리/)
-   오브젝트 스토리지에는 SQL도, JOIN도, 트랜잭션도 없다. **"이 키의 파일 줘"**가 거의 전부다. 대신 싸고, 크고, 튼튼하다

### 7\. 실무에서는 섞어 쓴다 - RAG 시스템 예시

문서 기반 RAG 시스템을 만들면 보통 저장소를 역할별로 나눈다.

```
업로드된 원본 파일 (PDF, HWP, 이미지)
   │
   ├─▶ 오브젝트 스토리지 (S3/MinIO)   : 원본 그대로 보관, 재처리할 때 다시 꺼냄
   │
   ├─▶ RDBMS (PostgreSQL)              : 추출 텍스트, 메타데이터, 권한, 처리 이력
   │
   └─▶ 벡터 DB (또는 pgvector/OpenSearch): 청크 임베딩, 의미 검색
                                         + (선택) Redis: 캐시·세션
```

| 저장소 | 넣는 것 | 하는 일 |
|---|---|---|
| **오브젝트 스토리지** | 원본 파일 | 증적 보관, 재처리 |
| **RDBMS** | 텍스트, 메타데이터, 이력, 권한 | 관리·조회·트랜잭션 |
| **벡터 DB** | 임베딩 | RAG 의미 검색 |
| **키-값 DB** | 자주 쓰는 결과, 세션 | 캐시로 응답 속도 개선 |

-   **원본을 따로 두는 이유**: 파싱 방식이나 임베딩 모델을 바꾸면 처음부터 다시 처리해야 하는데, 그때 원본이 필요하다
-   **메타데이터를 RDBMS에 두는 이유**: 권한·상태·이력처럼 **정합성이 중요한 관리 정보**는 트랜잭션이 되는 곳에 있어야 안전하다

### 8\. 상황별로 고르는 기준

| 이런 데이터·요구라면 | 이걸 먼저 떠올리자 |
|---|---|
| 정합성이 중요한 업무 데이터, 권한, 이력 | **RDBMS** |
| 구조가 자주 바뀌는 JSON 데이터 | **문서형 DB** (또는 RDBMS의 JSON 타입) |
| 아주 빠른 조회, 캐시, 세션 | **키-값 DB (Redis)** |
| 키워드 검색, 로그 분석 | **검색엔진 (OpenSearch)** |
| 의미가 비슷한 문서 찾기 (RAG) | **벡터 DB** 또는 **pgvector** |
| 관계를 따라가는 탐색 | **그래프 DB** |
| 큰 파일 원본, 백업, 이미지·영상 | **오브젝트 스토리지 (S3/MinIO)** |

### 마무리

한 줄로 줄이면, **RDBMS는 정확하게 관리하고, NoSQL은 용도별로 빠르고 유연하게 다루고, 벡터 DB는 의미로 찾고, 오브젝트 스토리지는 큰 파일을 싸게 보관한다.** 그리고 벡터 DB는 꼭 전용 제품일 필요가 없어서, 이미 PostgreSQL을 쓰고 있다면 pgvector부터 검토해볼 만하다.
