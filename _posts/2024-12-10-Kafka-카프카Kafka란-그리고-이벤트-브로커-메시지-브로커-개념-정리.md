### **카프카(Kafka)** 

**웹사이트, 어플리케이션, 센서 등에서 취합한 데이터를 스트림 파이프라인을 통해 실시간으로 관리하고**  
**보내기 위한 분산 스트리밍 플랫폼이다.**  
  
**데이터를 생성하는 어플리케이션과 데이터를 소비하는 어플리케이션 간의 중재자 역할을 함으로써**  
**데이터 전송 제어, 처리, 관리 역할을 한다. 카프카 시스템은 여러 요소(노드)와 함께 구성될 수 있어**  
**카프카 클러스터 라고 하기도 한다.**  
  
**다른 메시징 시스템과 마찬가지로 어플리케이션과 서버 간의 비동기 데이터 교환을 용이하게 하고,**   
**하루에 수 조개의 이벤트 처리가 가능하게 하는 역할을 한다.**  
  
**즉, 카프카는 플랫폼에 서비스를 연결하여 다양한 서비스에서 나오는 데이터 흐름을 실시간으로 제어하는  
서비스의 중추 역할을** **하는 플랫폼**

**즉, 분산형 메시징 시스템으로, 대량의 데이터를 실시간으로 처리하고 전달하기 위해**

**로그 기반의 게시/구독(pub-sub) 모델과 분산 스트리밍 플랫폼을 제공하는 도구**

* * *

#### **개발 배경**

**LinkedIn은 하나의 서비스에 과도하게 많은 시스템이 연결되어 있어 서비스를 유지하고 관리하는데 어려움을**

**겪었다.** **또한 시스템 유지보수 및 서비스 관리에도 많은 부담이 가해졌다.**  
**이를 극복하기 위해 컨플루언트 공동 창업자인 '제이 크랩스(Jay Kreps)'는 카프카(Kafka)라는  
메시징 분산 스트리밍 플랫폼을 고안하게 된다.** 

* * *

![](/assets/img/posts/280/1.png)

#### **기존 데이터 시스템의 문제점**

**각 애플리케이션과 DB가 End-to-End로 연결되어 있다 (각 파이프라인이 파편화되어 있음)**  
**그리고 요구사항이 늘어남에 따라 데이터 시스템 복잡도가 높아지면서 다음과 같은 문제가 발생하게 되었다.**

#### **1\. 시스템 복잡도 증가(Complexity)**

**→ 통합된 전송 영역이 없어 데이터 흐름을 파악하기 어렵고, 시스템 관리가 어려움**  
****→** 특정 부분에서 장애 발생 시 조치 시간 증가 (연결된 애플리케이션을 모두 확인하는 시간이 오래 걸린다)**  
****→** H/W 교체 및 S/W 업그레이드 시, 관리 포인트가 늘어나고 작업시간이 증가  
(연결된 애플리케이션에 Side Effect가 없는지 확인해야 함)**

#### **2. 데이터 파이프라인 관리의 어려움**

****→** 각 애플리케이션과 데이터 시스템 간의 별도의 파이프라인이 존재  
****→**** 파이프라인마다 데이터 포맷과 처리 방식이 다름**  
******→**** 새로운 파이프라인 확장이 어려워지면서 확장성 및 유연성이 떨어짐**

******→**** 데이터 불일치 가능성이 있어 신뢰도 감소**  

* * *

**이러한 문제를 해결하기 위해 새로운 시스템의 개발 필요성이 높아졌고**

**다음과 같은 목표를 가지고 새로운 시스템을 개발**

#### **목표**

**1\. 모든 시스템으로 데이터를 전송할 수 있고**

**2\. 실시간 처리도 가능하며**

**3\. 급속도로 성장하는 서비스를 위해** **확장이 용이한 시스템을 만들자.**  
  
**이렇게 모든 이벤트/데이터의 흐름을 중앙에서 관리하는 '카프카'를 개발하게 되었다.**

**카프카를 적용함으로써 앞서 말했던 문제점들이 완화되었다.**

#### **카프카로 인한 문제점 완화**

**1\. 모든 이벤트/데이터의 흐름을 중앙에서 관리할 수 있게 되었다.**  
**2\. 새로운 서비스/시스템이 추가돼도 카프카가 제공하는 표준 포맷으로 연결하면 되므로  
****확장성과 신뢰성이 증가**

**3\. 개발자는 각 서비스 간의 연결이 아닌, 서비스들의 비즈니스 로직에 집중 가능**  
  

![](/assets/img/posts/280/2.png)

### **발행 - 구독 모델 (Pub/Sub)**

**메시지 발행-구독 시스템에서는 데이터를 발행자가 직접 구독자에게 보내지 않는다.**  
**대신 발행자가 어떤 형태로든 메시지를 구분해서 발행 - 구독 시스템에 전송하면 구독자가 특정 부류의**  
**메시지를 구독할 수 있게 하는데 이때 발행된 메시지를 저장하고 중계하는 역할을 브로커가 한다.**  
  
**카프카는 발행-구독(pub/sub) 모델에서 브로커(broker)의 역할을 하고 있다.**  
**발행자(Publisher)와 구독자(Consumer) 사이에서 이벤트라 불리는 메시지를 카프카는 전달한다.**

* * *

### **카프카 구성요소**

#### **1\. Topic**

**\- 데이터를 논리적으로 분류하기 위한 단위**

**\- 각각의 메시지를 목적에 맞게 구분할 때 사용**  
**\- 메시지를 전송하거나 소비할 때, Topic을 반드시 입력**  
**\- Consumer는 자신이 담당하는 Topic의 메시지를 처리**  
**\- 한 개의 토픽은 한 개 이상의 파티션으로 구성**

#### **2\. Partition**

**\- 분산 처리를 위해 사용**  
**\- Topic 생성 시, Partition 개수를 지정할 수 있다 (파티션 개수 변경가능, 추가만 가능)**  
**\- 파티션이 1개라면 모든 메시지에 대해 순서가 보장**  
**\- 파티션 내부에서 각 메시지는 Offset(고유번호로) 구분**  
**\- 파티션이 여러 개라면 Kafka 클러스터가 라운드 로빈 방식으로 분배해서 분산처리되기 때문에 순서 보장 X**  
**\- 파티션이 많을수록 처리량이 좋지만 장애 복구 시간이 늘어남**

#### **3. Offset**

**\- 컨슈머에서 메시지를 어디까지 읽었는지 저장하는 값**  
**\- 컨슈머 그룹의 컨슈머들은 각각의 파티션에 자신이 가져간 메시지의 위치 정보(Offset)를 기록**  
**\- 컨슈머 장애 발생 후 다시 살아나도, 전에 마지막으로 읽었던 위치에서부터 다시 읽어 들일 수 있음**

#### **4\. Producer**

**\- 메시지를 만들어서 카프카 클러스터에 전송**  
**\- 메시지 전송 시, Batch처리 가능**  
**\- Key값을 지정하여 특정 파티션으로만 전송이 가능**  
**\- 전송 acks값을 설정하여 효율성을 높일 수 있다**  
**\- ACKS=0 -> 매우 빠르게 정송, 파티션 리더가 받았는지 알 수 없다.**  
**\- ACKS=1 -> 파티션 리더가 받았는지 확인. 기본값**  
**\- ACKS=****ALL -> 파티션 리더뿐만 아니라 팔로워까지 메시지를 받았는지 확인**

#### **5\. Consumer**

**\- 카프카 클러스터에서 메시지를 읽어서 처리**  
**\- 메시지를 Batch 처리 가능**  
**\- 한 개의 컨슈머는 여러 개의 토픽을 처리 가능**  
**\- 메시지를 소비하여도 메시지를 삭제하지 않는다. (Kafka Delete Policy에 의해 삭제)**  
**\- 한 번 저장된 메시지를 여러 번 소비도 가능**  
**\- 컨슈머는 컨슈머 그룹에 속함**  
**\- 한 개 파티션은 같은 컨슈머 그룹의 여러 개의 컨슈머에서 연결할 수 없다**  
**(즉, 같은 그룹의 여러 컨슈머가 같은 파티션에서 동시에 메시지를 읽을 수는 없다.  
Offset을 파티션 단위로 관리하기 때문에,** **여러 컨슈머가 동일한 파티션을 동시에 읽으면 Offset 관리가 혼잡)**

#### **6\. Broker**

**\- 실행된 카프카 서버**  
**\- 프로듀서와 컨슈머는 별도의 애플리케이션으로 구성되는 반면, 브로커는 카프카 자체**  
**\- 브로커(각 서버)는 Kafka Cluster 내부에 존재**  
**\- 서버 내부에 메시지를 저장하고 관리하는 역할을 수행**

* * *

### **주요 설계 특징**

#### **왜 하나의 Topic을 여러 개의 Partition으로 분산시키는가?**

**\- 병렬로 처리하기 위해 분산 저장**  
**\- 카프카의 토픽에 메시지가 쓰이는 것도 어느 정도 시간이 소비된다. 몇 천 건의 메시지가 동시에 카프카에 Write 되면** **병목현상이 발생할 수 있다.**  
**\- 따라서 파티션을 여러 개 두어서 분산 저장함으로써 Write 동작을 병렬로 처리할 수 있다.**  
**\- 다만, 한번 늘린 파티션은 절대 줄일 수 없기 때문에, 운영 중에 파티션을 늘려야 하는 건 충분히 검토 후 실행되어야 한다.** **(최소한의 파티션으로 운영하고 사용량에 따라 늘리는 것을 권장)**  
**\- 파티션을 늘렸을 때 메시지는 Round-Robin 방식으로 사용된다. 따라서 하나의 파티션 내에서는 메시지 순서가 보장되지만,** **파티션이 여러 개일 경우에는 순서가 보장되지 않는다.**

* * *

#### **이벤트 브로커와 메시지 브로커는 모두 분산 시스템에서 데이터를 전달하고 중재하는 역할을 하지만,  
주요 사용 목적과** **동작 방식에 차이가 있다.**

### **이벤트 브로커**

#### **주요 목적**

**시스템에서 발생하는 이벤트를 기록하고 구독자가 이벤트를 실시간으로 처리할 수 있도록 합니다.**

#### **작동방식**

**1\. 이벤트 중심**  
**\- 발생한 이벤트 (예 : 사용자가 주문을 완료)를 기록하여 시스템이 반응할 수 있도록 설계**  
**2\. 발행구독**  
**\- 모델에 주로 의존**  
**3\. 특징**  
**\- 이벤트 로그는 비휘발성 저장이 일반적이며, 구독자는 필요한 경우 이벤트를 재처리할 수 있음.**

#### **대표사례**

**\- Apache Kafka, AWS EventBridge, Google Pub/Sub 등.**

#### **사용사례**

**1\. 데이터 스트리밍**  
**\- 실시간으로 사용자 행동 데이터를 처리하여 대시보드에 표시**  
**2\. 이벤트 소싱**  
**\- 시스템의 상태를 이벤트 로그를 기반으로 재구성**

### **메시지 브로커**

#### **주요 목적**

**애플리케이션 간의 메시지 전달을 중재하여 데이터 교환 및 통신을 원활히 하는데 집중한다.**

#### **작동방식**

**1\. 지시형 메시징**  
**\- 메시지는 주로 작업이나 명령 (예: "주문생성" 또는 "이메일 발송요청")의 형태로 전달된다.**  
**2\. 점대점(Queue)또는 발행-구독 모델 사용**  
**3\. 특징**

**\- 일반적으로 메시지를 한번 소비하면 삭제 (비휘발성 저장 옵션도 있음)**

#### **대표사례**

**\- RabbitMQ, ActiveMQ, IBM MQ 등.**

#### **사용사례**

**1\. 동기화 작업**

**\- 주문 서비스가 배송 서비스에 데이터를 전달**  
**2\. RPC(원격 프로시저 호출) 형태로 동작**

**\- 배송 서비스가 메시지를 소비 후 메시지는 삭제**

#### **이벤트 브로커**

**\- 여러 서비스(재고관리, 결제시스템, 분석 대시보드 등)가 이벤트를 실시간으로 소비하여 각각 필요한 작업을 처리**

### **RabbitMQ는 왜 대규모 데이터 스트리밍에 적합하지 않은가?**

####   
**1. 메시지 저장 및 처리의 한계**

**\- RabbitMQ는 메시지를 큐에 저장하고 가능한 한 빨리 소비자에게 전달하도록 설계되어 있음**  
**\- 메시지를 오랜 시간 저장하거나 대량의 메시지를 처리하는데 비효율적**  
**\- 데이터가 빠르게 생성되고 소비자에 의해 즉시 소비되지 않으면, 큐에 메시지가 쌓이고**  
**성능 병목이 발생할 수 있다**

#### **2\. 스케일링 한계**

**\- RabbitMQ는 수평적 확장을 지원하지만, 데이터의 파티셔닝 및 클러스트링이 Kafka만큼 유연하지 않다**  
**\- 클러스터링과 큐 복제 설정이 복잡하며, 잘못 구성하면 성능 저하와 관리의 어려움을 초래**

#### **3\. 발행-구독 모델의 제약**

**\- RabbitMQ의 기본적인 발행-구독 모델은 지속적인 스트리밍 데이터의 높은 처리라량 처리하기보다는**  
**트랜잭션 기반 메시징에 더 적합**  
**\- 스트림 데이터 재생 기능이 부족하여, 과거 데이터를 소비자가 다시 처리해야 하는 상황에서 비효율적**

#### **4. 중앙 집중식 큐 관리**

**\- RabbitMQ는 각 메시지를 특정 큐로 전달하는 구조를 사용하므로, 큐가 특정 컨슈머에 과부하가 걸릴 경우**  
**병목 형상이 발생할 수 있다.**

#### **RabbitMQ가 더 적합한 사례**

**1\. 실시간 알림, 요청-응답 기반 통신**  
**2. 짧은 수명 주기를 가지는 메시지 처리**  
**3. 메시지 전달 보장이 필요한 워크로드**

* * *

### **Kafka가 대규모 데이터 스트리밍에 적합한 이유는?**

#### **1\. 분산 아키텍처**

**\- Kafka는 메시지를 파티션으로 나누어 클러스터의 여러 브로커에 저장하며, 이를 통해 높은 처리량을 유지하고 확장이 용이**

#### **2\. 메시지 저장 및 재생 기능**

**\- Kafka는 메시지를 디스크에 장기간 저장하며, 소비자는 필요할 때 언제든지 과거 데이터를 다시 읽을 수 있다**  
**\- 이러한 기능은 로그 데이터 분석, 실시간 스트리밍 데이터 처리에 특히 유용**

#### **3\. 고성능 및 확장성**

**\- Kafka는 초당 수백만 건의 메시지를 처리할 수 있도록 설계**

#### **4. 발행-구독 모델의 효율성**

**\- RabbitMQ보다 더 유연하고 강력한 발행구독 모델을 지원**

#### **Kafka가 더 적합한 사례**

**1\. 로그 및 이벤트 스트리밍**  
**2. 대규모 데이터 파이프라인**  
**3. 장기적인 메시지 저장 및 분석**
