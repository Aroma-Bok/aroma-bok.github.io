### 들어가며

"Langfuse를 도입해서 워크플로 엔진과 통합한다"는 얘기를 듣고 처음엔 감이 안 왔다. Langfuse는 **에이전트를 만드는 도구가 아니라, 에이전트가 일한 과정을 기록하고 평가하는 도구**다. 이걸 이해하려면 "관측성(Observability)"이라는 개념부터 알아야 해서, 같이 알아야 할 것들을 묶어서 정리한다.

(LLM 기초는 [LLM 기본 개념 정리](/posts/LLM-기본-개념-정리-토큰-컨텍스트-파라미터-GPU-메모리/), 프롬프트·Few-shot은 [Fine-tuning vs Few-shot·Many-shot vs RAG](/posts/Fine-tuning-vs-Few-shot-Many-shot-vs-RAG-LLM을-원하는-대로-동작시키는-방법/) 글 참고)

### 1\. 왜 LLM 서비스는 "관측"이 따로 필요한가

일반 웹 서비스는 같은 입력이면 같은 결과가 나온다. LLM 서비스는 그렇지 않아서 문제가 생겨도 원인을 찾기 어렵다.

-   **결과가 매번 다를 수 있다**: 같은 질문에도 답이 달라진다. "그때 왜 그렇게 답했지?"를 재현하려면 당시의 프롬프트·모델·파라미터·검색 결과가 다 필요하다
-   **단계가 많다**: 에이전트는 질문 이해 → 검색 → 재정렬 → 생성 → 검증처럼 여러 단계를 거친다. **어느 단계에서** 틀렸는지 알아야 고칠 수 있다
-   **프롬프트를 자주 바꾼다**: 바꾼 뒤 **좋아졌는지 나빠졌는지** 숫자로 비교해야 한다
-   **비용과 속도**: 호출마다 토큰 비용과 지연이 다르다. 어디서 돈과 시간이 새는지 봐야 한다
-   **품질 평가가 정답 비교로 안 끝난다**: "맞다/틀리다"가 아니라 루브릭이나 사람 평가가 필요하다

이걸 해결하는 영역이 **LLM 관측성(LLM Observability)**이고, Langfuse가 대표적인 오픈소스 도구다.

### 2\. 먼저 알아야 할 개념 - 관측성 기초

#### 관측성의 3요소

| 요소 | 뜻 | 예 |
|---|---|---|
| **로그(Log)** | "언제 무슨 일이 있었다"는 텍스트 기록 | `14:02:11 검색 결과 0건` |
| **메트릭(Metric)** | 숫자로 집계한 지표 | 평균 응답시간 2.3초, 오류율 1% |
| **트레이스(Trace)** | 요청 하나가 시스템을 거쳐 간 **전체 경로** | 질문 1건이 검색 → 생성 → 응답까지 간 흐름 |

LLM 관측성에서는 특히 **트레이스**가 중심이다. 에이전트의 여러 단계를 한 줄로 이어서 봐야 하기 때문이다.

#### Trace와 Span

-   **Trace**: 요청 1건의 전체 실행
-   **Span**: Trace 안의 한 구간 (검색 1회, 도구 호출 1회)
-   Span은 부모-자식 관계로 중첩된다. 병렬로 실행된 단계도 같은 부모 아래 나란히 기록된다

```
Trace: 사용자 질문 1건
├─ Span: 질문 분류
├─ Span: 문서 검색
│    └─ Span: 재정렬
├─ Span: 답변 생성
└─ Span: 답변 검증
```

#### OpenTelemetry (OTel)

-   Trace·Metric·Log를 수집하고 전달하는 **업계 표준 규격**
-   서로 다른 제품끼리 "이 요청은 같은 Trace다"라는 정보(trace context)를 주고받을 수 있게 해준다
-   OTel로 연결해두면 **특정 관측 도구에 덜 묶인다** (나중에 도구를 바꾸기 쉬움)
-   OTLP는 OTel 데이터를 보내는 전송 규격 이름이다

#### MLOps와 LLMOps

| | MLOps | LLMOps |
|---|---|---|
| 관리 대상 | 모델 학습·배포·모니터링 | 프롬프트·RAG·에이전트·평가 + 모델 |
| 주로 바뀌는 것 | 모델 가중치 | 프롬프트, 예시, 검색 인덱스, 워크플로 |
| 품질 확인 | 정확도 같은 정량 지표 | 루브릭, LLM 채점, 사람 평가 |

Langfuse는 LLMOps 중에서도 **관측 + 평가 + 프롬프트 관리**를 맡는다. 모델 배포나 GPU 모니터링은 다른 도구(MLOps·APM)의 영역이다.

### 3\. Langfuse란

**Langfuse는 LLM 애플리케이션을 위한 오픈소스 관측·평가 플랫폼**이다.

-   **라이선스**: 저장소 대부분이 MIT 라이선스이고, `ee`(Enterprise Edition) 폴더의 일부 기능만 상용 라이선스다
-   **설치**: 클라우드 서비스도 있지만 **직접 설치(self-hosting)**가 가능하고, 공식 문서상 인터넷 연결 없이 사내망·폐쇄망에도 구성할 수 있다
-   **연동**: Python/JS SDK, 각종 프레임워크 연동, **OpenTelemetry 기반** 수집, LiteLLM 같은 LLM Gateway 경유 수집을 지원한다

#### 주요 기능 5가지

| 기능 | 하는 일 |
|---|---|
| **Tracing (관측)** | LLM 호출뿐 아니라 검색·임베딩·API 호출까지 기록. 대화는 Session으로, 에이전트는 그래프로 시각화 |
| **Prompt Management** | 프롬프트 버전 관리, 라벨로 배포, 플레이그라운드에서 테스트 |
| **Evaluation (평가)** | LLM-as-a-Judge, 코드 평가기, 사용자 피드백, 사람 라벨링 |
| **Datasets & Experiments** | 평가용 데이터셋을 만들고, 설정을 바꿔가며 같은 데이터셋으로 비교 실험 |
| **Analytics** | 품질·비용·지연 대시보드, 알림 |

### 4\. Langfuse의 데이터 단위

| 용어 | 뜻 | 예 |
|---|---|---|
| **Trace** | 요청 1건 전체 | "환불 문의" 질문 1건 처리 |
| **Span** | 하위 실행 단위 | 문서 검색, 도구 호출 |
| **Generation** | LLM 호출 1회 (모델·프롬프트·토큰·지연 포함) | 답변 생성 호출 |
| **Session** | 여러 Trace를 묶은 대화 단위 | 한 사용자와의 대화 전체 |
| **Score** | 평가 점수 (숫자·범주·불리언) | 정확도 0.8, 사람 판정 "채택" |
| **Dataset** | 입력과 기대 결과의 묶음 | 정답이 정해진 평가 질문 100개 |
| **Experiment** | Dataset에 특정 설정을 돌린 결과 | 프롬프트 v3로 돌린 결과 vs v4 |

핵심은 **Trace에 Score를 붙인다**는 점이다. 실행 기록과 평가 점수가 연결되니 "점수가 낮은 건들은 어떤 프롬프트·어떤 검색 결과였나"를 거꾸로 추적할 수 있다.

### 5\. 예시 - RAG 챗봇 요청 하나가 기록되는 모습

```
Trace: "연차는 며칠까지 이월되나요?"  (trace_id, user_id, session_id)
├─ Span: 질문 재작성
│    └─ Generation: model=small, prompt=rewrite@v2, tokens=180, 0.4s
├─ Span: 하이브리드 검색   (query, 문서 ID 5개, 점수)
├─ Span: 재정렬            (reranker 버전, 순위 변화)
├─ Span: 답변 생성
│    └─ Generation: model=large, prompt=answer@v7, tokens=1,200, 2.1s
└─ Span: 답변 검증
     └─ Score: groundedness = 0.92 (LLM Judge)

(나중에) Score: user_feedback = like  ← 사용자 평가가 같은 Trace에 붙음
```

이렇게 남겨두면,

-   답이 틀렸을 때 **검색이 문제였는지, 생성이 문제였는지** 바로 구분된다
-   어느 단계가 느린지, 어느 모델 호출이 비싼지 보인다
-   같은 질문을 **당시와 같은 조건으로 재현**할 수 있다

### 6\. 프롬프트 관리 - 버전과 라벨

프롬프트를 코드 안에 박아두면 바꿀 때마다 배포해야 하고, 누가 언제 왜 바꿨는지 남지 않는다. 프롬프트 관리 기능은 이걸 **버전 관리되는 데이터**로 다룬다.

-   **버전**: 수정할 때마다 v1, v2, v3…
-   **라벨**: `staging`, `production`처럼 버전에 붙이는 이름표. 앱은 "production 라벨이 붙은 버전"을 가져다 쓴다
-   **배포 = 라벨 이동**: 새 버전을 검증한 뒤 production 라벨을 옮기면 배포, 되돌리면 롤백
-   **캐시**: 매 호출마다 프롬프트를 조회하지 않도록 앱 쪽에 캐시해 둔다

운영에서 흔히 지키는 규칙:

-   **"latest(최신)" 자동 사용 금지**: 검증 안 된 버전이 바로 운영에 나가지 않게
-   **원장은 한 곳만**: 프롬프트를 두 시스템에서 각각 수정할 수 있으면 버전이 어긋나고 감사가 깨진다

### 7\. 평가 - LLM 품질을 숫자로 보는 방법

| 평가 방식 | 설명 |
|---|---|
| **LLM-as-a-Judge** | 다른 LLM에게 루브릭을 주고 채점하게 함 |
| **코드 평가기** | JSON 형식 준수, 금지어 포함 여부 같은 규칙 검사 |
| **사용자 피드백** | 좋아요/싫어요, 별점 |
| **사람 라벨링 (Annotation)** | 전문가가 직접 점수·판정 |

#### Dataset → Experiment → 회귀 평가

1.  정답(또는 기대 결과)이 있는 **평가 데이터셋**을 만든다 (Gold Set)
2.  프롬프트·모델·검색 설정을 바꿀 때마다 같은 데이터셋으로 **실험**한다
3.  이전 버전보다 **점수가 떨어지지 않는지(회귀)** 확인하고 배포한다

#### LLM Judge를 믿어도 되나?

LLM이 LLM을 채점하면 편향이 있을 수 있다. 그래서 **사람 평가와 얼마나 일치하는지**를 같이 본다.

-   **Cohen's Kappa**: 두 평가자의 판정이 우연 이상으로 일치하는 정도 (범주형)
-   **Pearson 상관**: 두 점수가 같은 방향으로 움직이는 정도
-   **MAE (평균 절대 오차)**: 두 값이 평균적으로 얼마나 차이 나는지

### 8\. 워크플로 엔진(에이전트 빌더)과의 관계

여기가 처음에 가장 헷갈렸던 부분이다. **Langfuse는 워크플로를 실행하지 않는다.**

| 역할 | 에이전트 빌더 / 워크플로 엔진 | Langfuse |
|---|---|---|
| 워크플로 설계 (노드 연결) | **주관** | 안 함 |
| 실행·분기·재시도 | **주관** | 과정을 관측 |
| RAG·도구 호출 | **주관** | 입출력·지연 기록 |
| LLM 호출 | **주관** | 모델·토큰·지연·응답 기록 |
| 품질 평가 | 평가 에이전트 실행 | 점수 저장·비교·분석 |
| 프롬프트 | 실행 | 버전·실험·배포 관리 (원장을 어디로 할지는 결정 필요) |

**비유**: 워크플로 엔진은 **생산 라인**, Langfuse는 그 라인을 비추는 **CCTV + 품질 검사실**이다.

#### 통합할 때 지키는 원칙

-   **실행 책임과 관측 책임을 분리**한다
-   **ID를 서로 연결**한다: 워크플로의 실행 ID ↔ Langfuse Trace ID ↔ 업무 데이터 ID
-   **OpenTelemetry 우선**으로 연결해서 두 제품이 서로에게 덜 묶이게 한다
-   **관측이 죽어도 업무는 돌아가야 한다**: 기록은 비동기로 보내고(버퍼), Langfuse 장애가 워크플로 중단으로 번지지 않게 차단(circuit breaker)한다

#### 통합 전에 워크플로 엔진 쪽에서 확인할 것

-   OpenTelemetry trace context를 다음 단계로 넘겨주는가
-   노드 실행 전후에 입력·출력·오류·지연을 꺼낼 수 있는 Hook이 있는가
-   OTLP Exporter나 Langfuse SDK를 붙일 수 있는가
-   워크플로·노드·실행(Run)마다 고유 ID가 있는가
-   외부 프롬프트 저장소에서 **명시 버전**을 가져와 쓸 수 있는가
-   병렬 실행의 부모-자식 관계가 유지되는가
-   스트리밍 응답의 첫 토큰 시간·전체 지연을 잴 수 있는가

### 9\. 직접 설치(Self-hosting) 구성

공식 문서 기준 구성 요소는 이렇다.

| 구성 요소 | 역할 | 저장소 종류 |
|---|---|---|
| **Langfuse Web** | 화면(UI)과 API 제공 | 애플리케이션 |
| **Langfuse Worker** | 들어온 이벤트를 비동기로 처리 | 애플리케이션 |
| **PostgreSQL** | 사용자·프로젝트·프롬프트 같은 트랜잭션 데이터 | 관계형 DB |
| **ClickHouse** | Trace·Span 같은 대량 관측 데이터 분석 | 컬럼형 분석 DB |
| **Redis / Valkey** | 캐시와 작업 큐 | 키-값 DB |
| **S3 / Blob 스토리지** | 원본 이벤트와 첨부 파일 | 오브젝트 스토리지 |

저장소마다 역할이 왜 다른지는 [DB 종류와 스토리지 개념 정리](/posts/DB-종류와-스토리지-개념-정리-RDBMS-NoSQL-벡터DB-오브젝트-스토리지/) 글과 그대로 연결된다. 특히 **ClickHouse**는 "엄청 많이 쌓이는 기록을 빠르게 집계"하는 데 특화된 컬럼형 DB라서 Trace 분석에 쓰인다.

### 10\. 기밀 데이터를 다룰 때 주의할 점

관측 도구는 **입력과 출력을 통째로 저장**하기 쉬워서, 민감한 데이터를 다루면 오히려 유출 지점이 될 수 있다.

-   **최소 수집**: 운영 환경은 ID·해시·점수 위주로 남기고, 원문은 꼭 필요한 곳만
-   **마스킹**: 개인정보·민감정보는 보내기 전에 걸러낸다
-   **환경 분리**: 개발·검증·운영 프로젝트와 API Key를 나누고 서로 조회 못 하게
-   **권한 분리**: 운영자·평가자·감사자 역할을 나눈다
-   **보존기간**: Trace 종류별로 보관 기간과 자동 삭제 정책을 둔다
-   **외부 통신 차단**: 폐쇄망이면 텔레메트리·자동 업데이트가 밖으로 나가지 않게

### 11\. 같이 공부하면 좋은 순서

1.  **관측성 기초**: 로그·메트릭·트레이스, Trace·Span
2.  **OpenTelemetry**: trace context가 어떻게 전달되는지
3.  **LLM 애플리케이션 구조**: RAG, 에이전트, 프롬프트 (기존 정리 글들)
4.  **Langfuse 데이터 모델**: Trace / Generation / Score / Dataset
5.  **프롬프트 버전·라벨 운영**과 **회귀 평가**
6.  **평가 지표**: LLM-as-a-Judge, Kappa·Pearson·MAE

### 마무리

한 줄로 줄이면, **에이전트 빌더가 일을 "하고", Langfuse는 그 일이 "어떻게 됐는지 기록하고 채점"한다.** 그래서 Langfuse를 이해하려면 도구 사용법보다 먼저 **Trace·Span(무엇을 기록하나)**, **OpenTelemetry(어떻게 연결하나)**, **평가·회귀(어떻게 좋아졌다고 증명하나)**를 알아야 한다.
