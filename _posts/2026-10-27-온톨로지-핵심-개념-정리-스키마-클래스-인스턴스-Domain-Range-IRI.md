### 들어가며

온톨로지를 공부하면서 가장 헷갈리는 것은 비슷해 보이는 용어들의 경계다. 온톨로지와 스키마, 온톨로지와 지식그래프, 클래스와 인스턴스, Object Property와 DataType Property, Domain과 Range 같은 것들이다. 이 글은 프로테제(Protégé)에서 온톨로지를 만들 때 바로 부딪치는 **핵심 개념**만 따로 모아 정리한다. 왜 온톨로지를 쓰는지, 모델링 절차는 어떻게 되는지는 별도 글(온톨로지 기초 정리)에서 다룬다.

### 1. 온톨로지 = 스키마, 지식그래프 = 온톨로지 + 데이터

가장 먼저 구분할 것은 온톨로지와 지식그래프다.

- **온톨로지**: 스키마에 해당한다. 어떤 종류의 개체가 있고, 어떤 관계를 가질 수 있는지 정의한 **틀**이다. 아직 데이터는 담기지 않았다.
- **지식그래프**: 온톨로지(틀)에 **실제 데이터(인스턴스)** 를 채운 결과물이다.

**온톨로지 + 실제 데이터 = 지식그래프**

RDB와 비교하면 쉽다.

| 구분 | RDB | 온톨로지 |
|---|---|---|
| 틀 정의 | 테이블, 컬럼 | 클래스, 속성 |
| 실제 데이터 | 행(row) | 인스턴스 |

RDB에서 스키마로 테이블과 컬럼을 정의하듯, 온톨로지에서는 클래스와 속성을 정의한다. 짧게 말하면 **온톨로지는 스키마를 모델링하는 것**이라고 할 수 있다.

다만 온톨로지는 일반적인 DB 스키마보다 표현력이 크다. 테이블 구조뿐 아니라 "A는 B의 하위 개념이다", "이 관계의 반대 방향 관계는 이것이다" 같은 **의미와 논리(Axiom)** 까지 담고, 추론기가 이를 이용해 새 사실을 도출한다. 또 "지식그래프"라는 말은 실무에서 온톨로지 없이 만든 그래프 데이터를 가리키는 데도 느슨하게 쓰이므로, 글이나 대화에서 어떤 의미인지 확인할 필요가 있다.

### 2. 의미 표현의 스펙트럼

데이터에 의미를 붙이는 방법은 한 가지가 아니라 단계가 있다. 단순한 것에서 표현력이 큰 것 순으로 이렇게 본다.

1. **용어집(Glossary)**: 용어와 그 정의를 나열한 목록
2. **택소노미(Taxonomy)**: 용어를 **계층(상위/하위)** 으로 분류한 것. 예: 장비 → 펌프 → 원심펌프
3. **시소러스(Thesaurus)**: 계층에 더해 **동의어, 관련어** 같은 용어 간 관계를 담은 것
4. **스키마(Schema)**: 데이터의 구조와 제약을 정의한 것
5. **온톨로지(Ontology)**: 개념, 관계, **논리 규칙**까지 형식으로 정의해서 컴퓨터가 추론할 수 있는 것

뒤로 갈수록 **의미를 기계가 이해하고 처리할 수 있는 정도**가 커진다. 반대로 만드는 비용도 커진다. 그래서 필요한 수준까지만 만드는 것이 중요하다. 예를 들어 단순한 분류 체계만 필요하다면 택소노미나 시소러스로 충분하고, 이를 표현하는 어휘로 SKOS가 쓰인다.

### 3. 온톨로지 구성요소 4가지

1. **클래스(Class)**: 공통된 성질을 가진 개체들의 묶음. 예: `장비`, `사람`
2. **인스턴스(Instance)**: 클래스에 속하는 실제 개체 하나하나. 예: `장비A`
3. **속성(Property)**: 개체와 개체를 잇는 **관계**, 또는 개체에 붙는 **값**
4. **제약(Axiom)**: 항상 참이어야 하는 명제. 예: "펌프는 장비의 하위 클래스다"

### 4. 클래스와 인스턴스의 경계는 상대적이다

클래스와 인스턴스를 나누는 기준은 절대적이지 않고 **모델링 목적**에 따라 달라진다.

- **일반적인 지식 수준**: 자동차 모델 `GV90`은 `자동차`라는 클래스의 인스턴스다.
- **중고거래 앱**: 같은 `GV90`이라도 시장에 나온 개별 차량들(2023년식 흰색 GV90, 2024년식 검정 GV90)이 인스턴스고, `GV90`은 그 차량들을 묶는 **클래스**가 된다.

이유는 "내가 다루는 가장 작은 단위가 무엇인가"가 도메인마다 다르기 때문이다. 개별 개체로 추적해야 하는 것이 인스턴스이고, 그 개체들을 묶어서 설명하는 것이 클래스다. 그래서 모델링을 시작할 때는 **범위와 CQ를 먼저 정해야** 클래스와 인스턴스를 정할 수 있다.

참고로 OWL 2에는 같은 이름을 클래스이면서 동시에 인스턴스로 쓸 수 있는 punning이라는 기능이 있다. 다만 처음 모델링할 때는 구분해서 쓰는 편이 안전하다.

### 5. 상위 클래스와 하위 클래스

**상위 클래스와 하위 클래스는 같은 종류의 개념이어야 한다.** 하위 클래스는 "A는 B의 한 종류다(is-a)"가 성립해야 한다.

- 맞는 예: `펌프`는 `장비`의 한 종류다 → `펌프`를 `장비`의 하위 클래스로 둔다.
- 틀린 예: `바퀴`는 `자동차`의 한 종류가 아니라 **일부(part-of)** 다 → 하위 클래스가 아니라 별도 클래스와 관계(`hasPart`)로 둔다.

하위 클래스의 모든 인스턴스는 자동으로 상위 클래스의 인스턴스이기도 하다. 그래서 `장비A`가 `펌프`의 인스턴스라고만 적어도 `장비A`는 `장비`로 취급된다. 이 성질이 상속과 추론의 기반이 된다.

### 6. 속성: Object Property와 DataType Property

속성은 두 종류다. 트리플(**주어 - 서술어 - 목적어**) 관점에서 보면 목적어 자리에 무엇이 오느냐가 다르다.

- **Object Property**: 목적어가 **다른 인스턴스**다. 개체와 개체를 잇는 관계다. 예: `장비A - 설치위치 - 공장1`
- **DataType Property**: 목적어가 **값**(문자열, 숫자, 날짜 등)이다. 예: `장비A - 용량 - 120`

그래프로 보면 Object Property는 노드와 노드를 잇는 엣지이고, DataType Property는 노드에 붙는 값이다. 구분 기준은 오른쪽 끝이 **자기 속성과 관계를 더 가질 수 있는 대상(개체)** 이냐, 그냥 **값**이냐다.

Object Property는 클래스 사이의 관계 규칙을 정의하지만, **실제 연결은 인스턴스끼리** 일어난다. "`설치위치`는 `장비`에서 `공장`으로 가는 관계"라고 클래스 수준에서 선언해 두고, 실제 데이터에서는 `장비A`와 `공장1`이 연결된다.

### 7. Domain과 Range

속성이 **어떤 클래스에서 시작해서 어떤 타입으로 가는지**를 정하는 것이 Domain과 Range다.

- **Domain(정의역)**: 이 속성의 **주어**가 될 수 있는 클래스
- **Range(치역)**: 이 속성의 **목적어**가 될 수 있는 클래스 또는 데이터 타입

예를 들면 이렇다.

- `name` - Domain - `Person`
- `name` - Range - `String`

의미는 "`name`이라는 속성은 `Person`의 것이고, 값은 문자열이다"이다. 이 선언은 DataType Property의 예이고, Object Property라면 `설치위치` - Domain - `장비`, Range - `공장`처럼 Range에 클래스가 온다.

**상속으로 반복을 줄일 수 있다.** 모든 클래스마다 `name`을 따로 주지 않고, 공통 상위 클래스에 `name`의 Domain을 주면 하위 클래스의 인스턴스가 모두 이를 쓸 수 있다. 하위 클래스의 인스턴스는 상위 클래스의 인스턴스이기도 하기 때문이다. 다만 Domain을 최상위 클래스(`owl:Thing`)로 두면 "모든 것이 이 속성을 가질 수 있다"가 되어 정보량이 거의 없으므로, 실제로는 속성을 공통으로 갖는 **가장 가까운 상위 클래스**에 두는 편이 좋다.

**자주 하는 오해: Domain/Range는 입력 검증이 아니다**

"`name`의 Domain이 `Person`이면 모든 `Person`은 `name`을 가져야 한다"고 이해하기 쉬운데, 그렇지 않다. OWL의 Domain과 Range는 **제약이 아니라 추론 규칙**이다.

- 의미: "`name`을 가진 것은 `Person`이다."
- 동작: 어떤 개체에 `name`이 붙어 있으면, 추론기는 그 개체를 `Person`이라고 **추론**한다. 오류로 막는 것이 아니다.
- 모순이 나는 경우: 그 개체가 `Person`과 겹치지 않는(disjoint) 다른 클래스로 선언되어 있다면 그때 추론기가 모순을 알려 준다.

"`Person`은 반드시 `name`을 가져야 한다"를 표현하려면 Domain/Range가 아니라 `Person`에 `name`의 **최소 개수 제약(min cardinality 1)** 을 건다. 그리고 OWL은 **열린 세계 가정(Open World Assumption)** 을 쓰기 때문에 `name`이 없는 `Person`이 있어도 "오류"가 아니라 "아직 모르는 값이 있을 수 있다"로 해석한다. 값이 누락됐는지 실제로 검증하고 싶다면 SHACL 같은 별도의 검증 도구를 쓴다.

### 8. owl:Thing

프로테제에서 클래스 목록을 열면 맨 위에 `owl:Thing`이 있다. **`owl:Thing`은 OWL이 기본으로 제공하는 최상위 클래스로, 모든 개체(인스턴스)가 속한 클래스**다.

- 내가 만든 모든 클래스는 암묵적으로 `owl:Thing`의 하위 클래스다.
- 모든 인스턴스는 `owl:Thing`의 인스턴스다.
- 반대편에 **`owl:Nothing`** 이라는 최하위 클래스가 있다. 인스턴스가 하나도 없는 빈 클래스이고, 추론기가 모순을 보고할 때 "이 클래스는 `owl:Nothing`과 같다(= 존재할 수 없다)"라는 형태로 나타난다.

그래서 새 클래스를 만들면 프로테제는 기본적으로 `owl:Thing` 아래에 붙인다. 계층을 만들 때는 이 밑에서 시작한다고 생각하면 된다.

### 9. IRI

**IRI(Internationalized Resource Identifier)** 는 온톨로지 안의 요소를 **전 세계에서 유일하게 식별하는 이름표**다. 프로테제에서 온톨로지를 만들 때 가장 먼저 정하는 것이 **온톨로지 전체의 ID**인 온톨로지 IRI다.

- 온톨로지 IRI: `http://example.org/equipment`
- 클래스 IRI: `http://example.org/equipment#Pump`
- 인스턴스 IRI: `http://example.org/equipment#장비A`

프로테제에서는 보통 `온톨로지 IRI + # + 이름`으로 개별 요소의 IRI가 만들어진다.

**IRI를 어디에 쓰는가**
- **고유 식별**: 이름이 같아도 IRI가 다르면 다른 개체다. 부서마다 `Pump`를 다른 뜻으로 써도 충돌하지 않는다.
- **재사용(import)**: 다른 온톨로지의 IRI를 가져오면 그 안의 클래스와 속성을 그대로 쓸 수 있다.
- **데이터 통합**: 서로 다른 시스템의 데이터가 같은 IRI를 가리키면 같은 대상으로 합쳐진다.
- **질의**: SPARQL에서 `PREFIX : <http://example.org/equipment#>`처럼 접두어로 선언해 두고 `:Pump`처럼 짧게 쓴다.

**주의할 점**
- IRI는 이름표이지 **실제로 접속되는 URL일 필요는 없다.**
- 실습에서는 프로테제 기본값을 써도 되지만, 실제로 공유하려면 조직이 관리하는 도메인 기반 IRI로 정하는 것이 좋다.
- 공유한 IRI를 나중에 바꾸면 참조가 깨지므로 처음에 신중하게 정해야 한다.

### 정리

| 개념 | 한 줄 요약 |
|---|---|
| 온톨로지 | 스키마(틀). 개념, 관계, 논리를 정의 |
| 지식그래프 | 온톨로지 + 실제 데이터 |
| 클래스 / 인스턴스 | 개체들의 묶음 / 실제 개체 (경계는 모델링 목적에 따라 상대적) |
| 상위/하위 클래스 | is-a(한 종류다) 관계여야 함. part-of는 아님 |
| Object Property | 인스턴스와 인스턴스를 잇는 관계 |
| DataType Property | 인스턴스와 값을 잇는 속성 |
| Domain / Range | 속성의 주어 / 목적어 타입. 검증이 아니라 추론 규칙 |
| owl:Thing | 모든 개체가 속한 최상위 클래스 |
| IRI | 요소를 전 세계에서 유일하게 식별하는 이름표 |
