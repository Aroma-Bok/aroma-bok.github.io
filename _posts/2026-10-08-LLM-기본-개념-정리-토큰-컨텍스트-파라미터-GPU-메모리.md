### 들어가며

LLM 관련 회의를 하다 보면 "컨텍스트 32K", "max 토큰 8K", "70B 모델", "fp8" 같은 말이 아무렇지 않게 오간다. 대충 감으로 알던 것들을 **어디까지가 기본 상식이고 어디부터가 엔지니어 영역인지** 기준으로 다시 정리해본다.

### 1\. 개념 지도 - 지금 배우는 게 어디에 속하나

```
AI
└─ 머신러닝
   └─ 딥러닝
      └─ 생성형 AI / LLM
         ├─ ① 모델 이해   : 토큰, 파라미터, 컨텍스트          (기본)
         ├─ ② 활용 기법   : 프롬프트, RAG, 에이전트            (기본~중급)
         ├─ ③ 학습        : Fine-tuning, LoRA                  (중급)
         ├─ ④ 서빙·인프라 : 양자화, GPU 메모리, KV 캐시        (중급, 엔지니어 영역)
         └─ ⑤ 운영(LLMOps): 버전·로그·평가·비용 모니터링       (운영/관리 영역)
```

-   **①·②**: LLM 프로젝트에 있다면 직군과 상관없이 알아야 하는 기본기
-   **③·④**: 원리만 이해하고, 세부 수치는 담당 엔지니어와 같이 보는 수준이면 충분
-   **⑤**: 관리 화면·운영 체계를 만드는 입장이라면 가장 깊게 봐야 하는 영역

### 2\. 토큰(Token)

LLM은 글자나 단어 대신 **토큰**이라는 조각 단위로 글을 읽고 쓴다.

-   **영어**: 평균적으로 1토큰 ≈ 0.75단어 (예: "innovation" → `innov` + `ation` = 2토큰)
-   **한국어**: 같은 내용이어도 토큰이 더 많이 든다 (모델·토크나이저마다 다름)
-   **K 단위**: 32K = 약 3만 2천 토큰, 128K = 약 12만 8천 토큰
-   정확한 개수는 모델의 **토크나이저**로 직접 세어봐야 한다

중요한 건 숫자가 **토큰 하나의 길이가 아니라 토큰의 개수**라는 점이다.

### 3\. 컨텍스트 길이 vs max 토큰

모델 스펙표에 자주 같이 나오는 세 숫자가 헷갈렸는데, 기준이 다르다.

| 항목 | 기준 | 의미 |
|---|---|---|
| Context Length (모델 설계값) | 입력 + 출력 합계 | 모델이 원래 감당할 수 있는 최대치 |
| Context Length (서빙 설정값) | 입력 + 출력 합계 | 실제 서비스에서 열어둔 한도. **실제로 쓸 수 있는 값** |
| max 토큰 | 출력만 | 한 번 응답할 때 생성할 수 있는 최대량 |

예를 들어 서빙 32K / max 토큰 8K라면,

```
|←────────── 서빙 32K (입력+출력 전체 한도) ──────────→|
|←──── 입력 (최대 약 24K) ────→|←── 출력 (최대 8K) ──→|
 시스템 프롬프트 + 검색 근거 + 예시      모델의 답변
```

-   **모델 설계값이 128K여도 서빙을 32K로 줄이는 경우가 많다**: GPU 메모리와 동시 처리량 때문
-   **출력이 max 토큰에 걸리면 문장 중간이라도 잘린다**: JSON 출력이면 괄호가 안 닫혀 파싱 오류가 날 수 있음

### 4\. 한도는 "호출 한 번" 기준이다

컨텍스트 한도는 대화 전체가 아니라 **API 호출 1회 기준**이다.

LLM은 호출이 끝나면 아무것도 기억하지 않는다(무상태, stateless). 대화가 이어지는 것처럼 보이는 건 **매 호출마다 이전 대화를 입력에 다시 넣어 보내기 때문**이다.

```
1회차: [질문1]                              → 답1
2회차: [질문1 + 답1 + 질문2]                → 답2
3회차: [질문1 + 답1 + 질문2 + 답2 + 질문3]  → 답3
```

-   그래서 **호출 횟수나 총 사용량에는 한도가 없다**
-   대신 대화가 길어지면 다시 보낼 이력이 쌓여서, 어느 순간 **한 번에 넣을 입력이 한도를 넘는다**
-   이걸 다루는 게 **메모리 관리**다
    -   **단기 메모리**: 현재 대화 흐름 유지 (이력을 매번 다시 넣음, 길면 요약·삭제)
    -   **장기 메모리**: 과거 정보를 DB에 저장해두고 필요한 부분만 검색해서 넣음

### 5\. 파라미터와 모델 크기(B)

**B는 Billion(10억)**이다. "70B 모델"은 **파라미터(가중치)가 700억 개**라는 뜻이다.

-   **파라미터(가중치)**: 모델이 학습으로 얻은 내부 숫자들. 모델의 지식 그 자체
-   모델 파일은 결국 **숫자 덩어리**라고 생각하면 된다

#### 크면 좋아지는 것

-   **지식량**: 더 많이, 더 정확하게 기억
-   **추론력**: 여러 단계를 거치는 복잡한 논리를 잘 따라감
-   **지시 이행**: 조건이 많아도 빠뜨리지 않음
-   **긴 글 이해**: 긴 입력에서 핵심과 관계를 잘 잡음

#### 크면 나빠지는 것

-   **느리다**: 계산할 숫자가 많아 응답이 늦음
-   **비싸다**: GPU 메모리를 많이 쓰고 호출 비용도 큼
-   **동시 사용자를 덜 받는다**: 아래 GPU 메모리 계산 참고

그리고 **크다고 무조건 이기지 않는다.** 학습 데이터 품질, 최신성, 추론 설정(reasoning effort), 프롬프트 방식에 따라 작은 최신 모델이 큰 구형 모델을 이기는 경우가 흔하다. 같은 모델도 설정만으로 성능 차이가 크게 난다.

그래서 실무에서는 **쉬운 작업은 작은 모델, 어려운 작업만 큰 모델**로 보내는 방식(모델 라우팅)을 많이 쓴다.

#### 주의: 같은 "B"가 다른 뜻일 때

"일 사용량 100B 달성" 같은 문장의 B는 파라미터가 아니라 **처리한 토큰 수**다. 회의에서 "100B"가 나오면 모델 크기 얘기인지 사용량 얘기인지 맥락을 확인하자.

### 6\. GPU 메모리 계산 - 왜 크기가 중요한가

#### 모델은 GPU 메모리에 통째로 올라가야 한다

LLM이 답을 하려면 파라미터 전부를 **GPU 메모리에 올려놓은 상태**여야 한다. **GPU 메모리는 책상, 모델은 펼쳐 놓을 책**이라고 생각하면 쉽다.

#### 숫자 하나의 크기 = 정밀도

| 저장 방식 | 숫자 1개 크기 | 비유 |
|---|---|---|
| 16비트 (FP16/BF16) | 2바이트 | 소수점 아래까지 꼼꼼히 적음 |
| 8비트 (FP8/INT8) | 1바이트 | 반올림해서 짧게 적음 |
| 4비트 (INT4 등) | 0.5바이트 | 더 과감하게 줄임 |

이렇게 비트 수를 줄이는 걸 **양자화(Quantization)**라고 한다. 메모리는 줄고, 정확도는 약간 떨어질 수 있다. 모델명 끝에 붙은 `_fp8` 같은 표기가 이 뜻이다.

#### 어림셈 공식

**필요 메모리 ≈ 파라미터 수 × 숫자 1개 크기**

-   70B × 2바이트(16비트) = **약 140GB**
-   70B × 1바이트(8비트) = **약 70GB**
-   10억 바이트 ≈ 1GB라서 **"B 숫자 × 바이트 수 = GB"**로 바로 계산된다

#### 모델만 올린다고 끝이 아니다: KV 캐시

사용자가 질문하면 모델은 처리 중인 대화에 대한 **작업 메모(KV 캐시)**를 GPU 메모리에 따로 만든다.

-   **대화가 길수록**, **동시 사용자가 많을수록** KV 캐시가 커진다
-   책상 비유로는 **책을 펼친 뒤 남은 자리**에서 사람들이 메모지를 펴고 작업하는 셈

예를 들어 80GB GPU 4장(총 320GB)이라면,

| 모델 (8비트 기준) | 모델이 차지하는 공간 | 남는 공간 |
|---|---|---|
| 70B | 약 70GB | 약 250GB → 동시 사용자 여유 |
| 250B | 약 250GB | 약 70GB → 빠듯함 |

큰 모델일수록 **동시에 받을 수 있는 사용자 수가 줄어드는 이유**가 이것이다. (실제 필요량은 서빙 엔진·설정에 따라 달라지는 어림셈)

### 7\. MoE - 전체 파라미터 vs 활성 파라미터

큰 모델 중에는 질문마다 **전문가(expert) 일부만 골라서 계산하는 구조(MoE, Mixture of Experts)**가 있다.

-   표기 예: **"250B total / 15B active"** → 전체는 250B, 한 번 계산에 쓰는 건 15B
-   **속도**는 작은 모델(활성 크기)에 가깝다
-   **메모리**는 전체 크기만큼 필요하다 (전문가를 전부 올려놔야 골라 쓸 수 있으니까)

### 8\. 모델에 지식을 넣는 3가지 방법

| 방법 | 하는 일 | 가중치 변경 | 특징 |
|---|---|---|---|
| **프롬프트 / Few-shot** | 지시문과 예시를 입력에 넣음 | 없음 | 가장 빠르고 쌈. 컨텍스트 한도 안에서만 가능 |
| **RAG** | 관련 자료를 검색해서 입력에 넣음 | 없음 | 최신 정보·사내 문서 반영. 검색이 틀리면 답도 틀림 |
| **Fine-tuning** | 추가 데이터로 가중치를 다시 학습 | 있음 | 말투·형식·행동을 몸에 익힘. 시간·비용·재학습 부담 |

-   **Few-shot**: 예시를 몇 개 넣는 것 (Zero-shot은 0개, One-shot은 1개, Many-shot은 아주 많이)
-   **CoT(Chain of Thought)**: 답 전에 단계별로 추론하게 하는 기법
-   **LoRA / QLoRA**: 모델 전체 대신 작은 부속 모듈(어댑터)만 학습하는 경량 Fine-tuning
-   요즘은 **모델은 그대로 두고 예시·규칙·검색 자료를 바꾸는 방식**(프롬프트 + RAG)으로 먼저 시작하고, 데이터가 쌓이면 선택적으로 Fine-tuning을 얹는 흐름이 흔하다

### 9\. OCR vs 텍스트 추출 vs VLM

문서를 LLM이 쓸 수 있는 텍스트로 바꿀 때도 방법이 갈린다.

| 파일 상태 | 방법 | OCR 필요 |
|---|---|---|
| 스캔 PDF, 사진 | **OCR**: 그림 속 글자를 인식 | 필요 |
| 워드·한글에서 저장한 PDF | **텍스트 추출**: 파일 안의 글자 데이터를 그대로 꺼냄 | 불필요 |
| HWP, PPT, Excel | **파서**로 형식 해석 (안에 박힌 이미지는 OCR) | 대부분 불필요 |

-   **전용 OCR 엔진**: Tesseract, PaddleOCR, 상용 Document AI류. 글자 좌표·신뢰도를 주고 결과가 일정함
-   **VLM(비전-언어 모델)**: 이미지를 직접 보고 이해. 레이아웃·맥락 이해는 강하지만 **없는 글자를 지어낼 위험**이 있음
-   실무에서는 **텍스트가 있으면 바로 추출, 이미지면 OCR, 구조화·분류는 LLM**으로 조합하는 경우가 많다

### 10\. 운영(LLMOps)에서 자주 나오는 말

관리·운영 쪽을 맡으면 결국 이 단어들이 화면과 기능이 된다.

-   **모델 레지스트리**: 사용 가능한 모델과 버전을 등록·관리하는 곳
-   **Alias**: 실제 모델명 대신 쓰는 논리 이름. 모델을 바꿔도 앱 코드는 그대로
-   **Shadow Test**: 새 모델을 운영 모델과 몰래 같이 돌려서 결과 비교
-   **Gold Set / 회귀 테스트**: 정답이 정해진 평가용 데이터로, 바꾼 뒤 성능이 떨어지지 않았는지 확인
-   **Rollback**: 문제가 생기면 이전 버전으로 되돌리기
-   **LLM-as-a-Judge**: LLM에게 채점 기준(루브릭)을 주고 다른 결과를 평가하게 하는 방식
-   **HITL(Human-in-the-Loop)**: 중요한 판단은 사람이 최종 확정
-   **Agent 하네스**: 에이전트의 모델·프롬프트·도구·검증·재시도를 묶어 실행·통제하는 틀
-   **temperature / reasoning effort**: 출력의 무작위성 / 추론 깊이 설정

### 마무리

정리하면, **토큰은 단위, 컨텍스트는 1회 호출의 한도, 파라미터는 모델의 크기, 양자화와 KV 캐시는 그 크기를 GPU에 어떻게 올리느냐의 문제**다. 기본 개념(①·②)은 회의를 따라가기 위해 꼭 알아야 하고, 서빙·인프라(③·④)는 원리 수준으로 이해한 뒤 엔지니어와 숫자를 맞춰보면 된다. 관리·운영을 맡는다면 결국 ⑤ LLMOps 용어들이 실제 화면과 기능으로 이어진다.
