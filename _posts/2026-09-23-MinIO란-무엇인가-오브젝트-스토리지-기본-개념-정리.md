## 들어가며

업무에서 파일 저장소로 MinIO를 마주쳤는데 제대로 정리해본 적이 없어서, 개념부터 실무에서 쓰이는 방식까지 한 번에 정리한다.

## 오브젝트 스토리지가 뭔가

파일을 저장하는 방식은 크게 세 가지로 나뉜다.

-   **블록 스토리지**: 디스크를 블록 단위로 잘라서 제공. DB 서버의 디스크처럼 저수준 I/O가 필요할 때 쓴다.
-   **파일 스토리지**: 우리가 흔히 아는 디렉토리/파일 구조(NFS 같은). 계층 구조가 있다.
-   **오브젝트 스토리지**: 파일(데이터) + 메타데이터 + 고유 Key를 하나의 "오브젝트"로 묶어서 평평한(flat) 네임스페이스인 "버킷"에 저장한다. 디렉토리 개념이 없고, Key 문자열이 경로처럼 보일 뿐이다.

대용량 비정형 데이터(이미지, 동영상, 로그, 백업 파일, AI 파이프라인의 원본 문서 등)를 다룰 때는 오브젝트 스토리지가 표준이고, 그 대표주자가 AWS S3다.

## MinIO 한 줄 정의

**MinIO는 Go로 작성된 오픈소스 고성능 오브젝트 스토리지 서버로, Amazon S3 API와 호환된다.** 즉 "내 서버/내 인프라에 직접 올리는 S3"라고 보면 된다.

## 왜 MinIO를 쓰는가

-   **S3 API 호환**: AWS SDK(boto3 등), s3cmd, 각종 라이브러리를 엔드포인트만 바꿔서 그대로 쓸 수 있다. S3용으로 짠 코드를 그대로 재사용 가능.
-   **클라우드 종속 탈피**: 온프레미스/폐쇄망 환경에서도 S3와 동일한 방식으로 파일을 다룰 수 있다.
-   **가볍고 빠름**: 단일 바이너리, Go로 작성. 컨테이너 하나로 바로 띄울 수 있다.
-   **대용량 비정형 데이터에 적합**: 이미지, 동영상, 로그, 백업, RAG 파이프라인의 원본 문서 저장 등.

## 핵심 개념

| 용어 | 설명 |
| --- | --- |
| Bucket | 최상위 저장 단위. S3의 버킷과 동일한 개념 |
| Object | 버킷 안에 저장되는 실제 데이터 + 메타데이터 + Key |
| Key | 오브젝트를 식별하는 문자열. 경로처럼 보이지만 실제 디렉토리 구조는 아니다 |
| Access Key / Secret Key | 인증용 키 쌍. AWS IAM 키와 같은 역할 |
| mc (MinIO Client) | CLI 도구. mc mb, mc cp 등으로 버킷과 오브젝트를 다룬다 |

## 아키텍처 살짝 보기

-   **Erasure Coding**: 여러 드라이브에 데이터와 패리티(복구용 정보)를 분산 저장해서, 일부 디스크가 죽어도 데이터를 복구할 수 있다. RAID 개념을 소프트웨어 레벨에서 구현한 것.
-   **Standalone 모드 vs Distributed 모드**: 개발/테스트는 단일 노드로 충분하지만, 운영 환경에서는 여러 드라이브로 구성된 분산 모드 + Erasure Coding이 기본이다.
-   버전 관리(Versioning), 버킷 이벤트 알림, 라이프사이클 정책 등 S3와 유사한 기능을 대부분 제공한다.

## Docker로 띄워보기

```routeros
docker run -p 9000:9000 -p 9001:9001 \
  -e "MINIO_ROOT_USER=admin" \
  -e "MINIO_ROOT_PASSWORD=admin1234" \
  minio/minio server /data --console-address ":9001"
```

-   9000번 포트: S3 호환 API
-   9001번 포트: 브라우저로 접속하는 관리 콘솔

## 기본 사용 흐름

1.  버킷 생성
2.  Access Key / Secret Key 발급
3.  AWS SDK나 mc client로 업로드·다운로드

S3 호환이라 기존 S3 코드에서 endpoint\_url만 바꾸면 그대로 동작한다.

```routeros
import boto3

s3 = boto3.client(
    "s3",
    endpoint_url="http://localhost:9000",
    aws_access_key_id="admin",
    aws_secret_access_key="admin1234",
)

s3.create_bucket(Bucket="my-bucket")
s3.upload_file("hello.txt", "my-bucket", "hello.txt")
```

## 실무에서는 이렇게 쓰인다

RAG/AI 에이전트 파이프라인 같은 구조에서는 사용자가 업로드한 원본 파일(PDF, 문서 등)을 MinIO에 저장하고, 파싱된 텍스트는 별도 검색엔진(OpenSearch 등)에 색인하는 식으로 역할이 나뉘는 경우가 많다. 이런 구조에서는 MinIO가 죽으면 "검색은 되는데 업로드만 실패"하는 증상으로 드러나는 경우가 많다 — 원본 파일을 저장할 곳이 없어지기 때문이다.

## 알아두면 좋은 점

-   **프로덕션에서는 분산 모드가 기본**이다. 단일 노드로 운영하면 디스크 장애 시 데이터가 그대로 유실된다.
-   MinIO 데이터 볼륨은 백업 대상에서 빠뜨리기 쉽다 — 별도 백업 전략이 필요하다.
-   오픈소스 서버와는 별도로 상용(엔터프라이즈) 라이선스가 있고, 최근 몇 년 사이 라이선스·기능 제공 정책이 여러 차례 바뀌었다는 이야기를 본 적이 있다. 이 부분은 확실치 않으니, 실제 도입 전에는 공식 문서에서 최신 라이선스 정책을 직접 확인하는 게 안전하다.

## 마무리

한 줄 요약: **MinIO는 "내 서버에 직접 놓는 S3"**. S3 API를 그대로 쓰면서 클라우드에 종속되지 않고 대용량 파일을 저장하고 싶을 때 선택하면 된다.
