### 들어가며

온톨로지를 처음 접하면 용어가 한꺼번에 쏟아진다. 그래프DB, RDF, OWL, LPG, Neo4j, 지식그래프, 트리플, CQ 같은 말이 서로 어떻게 연결되는지 한 번에 정리해 두려고 이 글을 쓴다. 이 글은 **왜 온톨로지를 쓰는지, 어떤 절차로 만드는지, LLM과 어떻게 만나는지**를 다룬다. 클래스와 인스턴스, Domain/Range, IRI 같은 세부 개념은 별도 글(온톨로지 핵심 개념 정리)에서 따로 정리한다.

**관련 용어**: 그래프DB, 네트워크, 노드, 엣지(관계), 온톨로지, RDF, OWL, Neo4j, LPG(Labeled Property Graph)

### 1. 왜 데이터를 그래프로 만드는가

데이터는 쌓이는 것만으로는 쓸모가 없고, 의미가 붙어야 쓸모가 생긴다. 흔히 이 흐름을 세 단계로 본다.

- **data**: 값 자체. 예: `37.5`, `불합격`
- **information**: 값에 맥락이 붙은 것. 예: "A 장비의 온도는 37.5도다"
- **knowledge**: 정보들 사이의 관계와 규칙까지 이해한 것. 예: "온도가 기준을 넘으면 A 장비는 점검 대상이다"

비유하면 **RDB는 data를 담는 그릇**이고, **그래프DB는 data 사이의 관계까지 담아 지식그래프를 만드는 그릇**이다. 관계가 많고 복잡할수록(여러 시스템의 데이터를 이어 붙이거나, 몇 다리 건너 연결된 정보를 찾아야 할 때) 그래프 형태가 유리하고, 많은 정보를 표현하기에는 온톨로지가 적합하다.

그래프의 가장 작은 단위는 **트리플(triple)** 이다. **주어(Subject) - 서술어(Predicate) - 목적어(Object)** 한 묶음이다.

- `장비A - 설치위치 - 공장1`
- `장비A - 종류 - 펌프`
- `공장1 - 소재지 - 울산`

**트리플이 모이면 그래프가 된다.** 위 세 줄에서 `장비A`, `공장1`이 공통으로 등장하므로 자연스럽게 하나의 연결된 그래프가 된다. 노드는 개체이고, 엣지는 관계다.

### 2. 온톨로지로 데이터를 구축하는 이유

온톨로지의 정의로 가장 많이 인용되는 문장은 **"공유된 개념화에 대한 형식적이고 명시적인 명세"** 이다. (Gruber의 정의에 Studer 등이 형식성과 공유성을 더한 것으로 알려져 있다.) 단어별로 풀면 이렇다.

- **개념화**: 어떤 영역에 어떤 종류의 것들이 있고 서로 어떤 관계인지에 대한 이해
- **명시적**: 머릿속에만 두지 않고 글로 드러내어 적는다
- **형식적**: 사람뿐 아니라 컴퓨터도 처리할 수 있는 규격으로 적는다
- **공유된**: 한 사람이나 한 시스템이 아니라 여러 주체가 합의한 것이다

결국 **나 혼자 쓰려고 만드는 것이 아니라, 다른 부서와 다른 시스템이 같이 쓰도록 합의된 규격으로 만드는 것**이다. 다른 사람이 봐도 같은 의미로 이해할 수 있어야 한다.

Java에 비유하면 이해가 쉽다. 객체지향에서 클래스를 한 번 정의해 두고 여러 곳에서 재활용하듯, 온톨로지도 개념(클래스)을 한 번 정의해 두고 여러 데이터와 시스템이 같은 정의를 가져다 쓴다. 의미가 비슷한 개념은 서로 연결해 둔다.

구축 목적을 정리하면 다음과 같다.

- **데이터 통합**: 서로 다른 시스템(예: PMS, ERP, 재무 시스템)의 데이터를 같은 개념 체계로 묶는다.
- **지식 표준화와 재사용**: 용어와 의미를 통일하고 다른 곳에서도 가져다 쓴다.
- **데이터 공유와 상호운용**: 부서와 시스템이 달라도 같은 의미로 주고받는다.
- **추론과 검증**: 명시적으로 적지 않은 사실을 규칙으로 도출하거나, 데이터가 규칙에 어긋나는지 검증한다.

활용 사례로 팔란티어(Palantir)가 자주 언급된다. 날씨와 모니터링 데이터 같은 여러 출처의 데이터를 하나의 개념 체계로 묶어 운영에 쓰는 방식이다. 참고로 팔란티어의 온톨로지는 개체와 관계뿐 아니라 개체에 대해 수행할 수 있는 행동(Action)까지 모델에 포함하는 것으로 알려져 있는데, 세부 구현은 확인이 필요하다.

### 3. RDB로도 되는데 왜 굳이 온톨로지인가

RDB도 테이블 설계를 잘 하면 공유할 수 있다. 그래서 온톨로지가 RDB를 대체한다기보다 **어떤 문제에서 더 유리한가**로 보는 것이 맞다.

- **의미의 위치**: RDB는 의미가 컬럼명이나 문서에 암묵적으로 담긴다. 온톨로지는 의미(클래스, 관계, 제약)가 데이터 모델 자체에 명시적으로 들어간다.
- **관계의 비중**: RDB는 관계를 외래키와 JOIN으로 간접 표현한다. 그래프는 관계가 데이터의 1급 요소다.
- **스키마 유연성**: RDB는 스키마 변경이 비싸다(마이그레이션). 온톨로지와 그래프는 새 클래스나 관계를 덧붙이기가 상대적으로 쉽다.
- **통합**: 서로 다른 시스템의 RDB는 컬럼명과 코드가 제각각이다. 온톨로지는 공통 개념에 각 시스템의 데이터를 매핑해서 묶는다.
- **추론**: RDB는 저장된 값만 조회한다. 온톨로지는 규칙으로 새 사실을 도출할 수 있다. 예를 들어 `펌프`가 `장비`의 하위 클래스라면, `장비A`가 `펌프`라는 사실만으로 `장비A`는 `장비`라는 결론이 나온다.

반대로 정형 데이터를 대량으로 집계하는 업무는 RDB가 여전히 더 적합하다. 온톨로지는 모델링 비용이 들기 때문에 통합, 의미 공유, 추론이 필요한 경우에 가치가 있다.

### 4. 표현 방식과 쿼리 방식

온톨로지와 지식그래프를 구현하는 방식은 크게 두 계열이다.

**RDF/OWL 계열 (시맨틱 웹 표준)**
- **RDF**: 모든 것을 트리플로 표현하고, 개체와 관계를 IRI로 식별한다. 서로 다른 출처의 데이터를 IRI로 합치기 쉽다.
- **OWL**: RDF 위에 클래스, 속성, 제약(Axiom)을 정의하는 온톨로지 언어다. 추론기(reasoner)가 규칙에 따라 새 사실을 도출하거나 모순을 검사한다.
- 질의 언어는 **SPARQL**이다.

**LPG(Labeled Property Graph) 계열**
- 노드와 관계에 라벨을 붙이고, 노드와 관계 모두 key-value 속성을 가질 수 있다.
- 대표 제품이 **Neo4j**이고, 질의 언어는 **Cypher**다.
- 관계에 속성을 바로 붙일 수 있고 개발자가 쓰기 쉽다. 반면 OWL 수준의 의미 규칙과 추론은 기본 기능이 아니다. Neo4j에서 RDF/OWL을 다루려면 neosemantics(n10s) 같은 플러그인이 필요하며, 지원 범위는 확인이 필요하다.

정리하면 **온톨로지는 모델(설계)이고, Neo4j 같은 그래프DB는 그 모델을 담을 수 있는 저장소 중 하나**다. Neo4j가 곧 온톨로지는 아니다.

같은 질문("불합격 판정을 받은 장비는?")을 두 언어로 쓰면 이런 모양이다.

```
-- SPARQL
SELECT ?e WHERE {
  ?i a :Inspection ;
     :target ?e ;
     :result "불합격" .
}

-- Cypher
MATCH (i:Inspection {result: '불합격'})-[:TARGET]->(e:Equipment)
RETURN e
```

### 5. 온톨로지의 새로운 사용자: LLM

온톨로지의 목적은 데이터 통합과 의미 공유로 그대로인데, 사용자가 사람과 시스템에서 **LLM**으로 넓어지고 있다. 흐름은 **시맨틱 웹 → 기업 지식그래프 → LLM + 그래프**로 볼 수 있다. 온톨로지의 가장 중요한 사용자는 LLM이라고 해도 과언이 아니다.

**LLM만으로는 부족한 이유**
- **환각**: 그럴듯하지만 틀린 내용을 만들어 낸다.
- **근거 부재**: 답이 어디서 나왔는지 출처를 대기 어렵다.
- **내부 지식 부재**: 학습 데이터에 없는 사내 지식과 최신 정보를 모른다.
- **일관성 부족**: 같은 질문에도 답이 달라질 수 있다.
- 공통 원인은 **무엇이 사실인지 판단할 기준 데이터가 없다**는 점이다.

**RAG와 그 한계**
- RAG는 질문과 관련된 문서를 찾아 LLM에게 함께 건네서 답하게 하는 방식이다.
- 일반적인 벡터 RAG는 문서를 조각(chunk)으로 나눠 임베딩하고, 질문과 **의미가 비슷한 조각**을 찾는다.
- 필요한 정보가 **여러 문서에 흩어져 있을 때**가 약점이다. 조각 하나하나는 질문과 비슷하지 않아서 검색되지 않고, 여러 조각을 연결해서 답해야 하는 질문(멀티홉)을 처리하기 어렵다.

**그래프 RAG**
- 데이터가 개체와 관계로 연결되어 있으므로, 관계를 따라가며 흩어진 정보를 모을 수 있다.

**벡터 RAG와 그래프 RAG의 차이**
- **검색 기준**: 벡터 RAG는 텍스트 유사도, 그래프 RAG는 관계를 따라가는 탐색이다.
- **강한 질문**: 벡터 RAG는 "이 문서에서 해당 부분이 뭐라고 하는가" 같은 국소적 질문에 강하다. 그래프 RAG는 "A와 연결된 B의 C는 무엇인가", 전체를 아우르는 집계와 요약 같은 질문에 강하다.
- **근거 제시**: 그래프는 어떤 경로로 답이 나왔는지 설명하기 쉽다.
- **구축 비용**: 벡터 RAG는 문서만 있으면 시작할 수 있다. 그래프 RAG는 개체와 관계를 추출하고 스키마를 설계해야 해서 비용이 크다.
- 실무에서는 둘을 함께 쓰는 하이브리드 구성도 많다.

한 줄로 정리하면 **LLM은 말을 잘하는 쪽이고, 온톨로지와 지식그래프는 사실과 기준을 주는 쪽**이다. 온톨로지가 있으면 문서에서 개체와 관계를 추출할 때 정해진 클래스와 관계만 쓰게 제한할 수 있고, 질문을 그래프 쿼리로 바꿀 때도 스키마를 기준으로 삼을 수 있다.

### 6. 온톨로지 모델링 절차

온톨로지를 구축하려면 기존 data를 지식으로 만드는 과정이 필요하다. 그 과정에서 분석과 모델링으로 **스키마**를 구성하고, 데이터를 그 스키마에 맞게 변환(트리플)해서 담는다. 데이터를 어떻게 담을지는 처음부터 생각해야 한다.

모델링은 보통 다음 7단계로 진행한다.

1. **범위 결정**: 어떤 질문에 답하려는 온톨로지인지, 어디까지 다룰지 정한다.
2. **재사용 검토**: 기존 어휘를 쓸 수 있는지 확인한다. 예: **SKOS**(분류체계와 시소러스 표현용), **schema.org**(웹 개체 어휘). 이미 있는 것을 쓰면 처음부터 만들 필요가 없고 다른 시스템과 호환된다.
3. **용어 나열**: 도메인에서 쓰는 용어를 모두 적는다.
4. **클래스 계층 정의**: 용어를 클래스로 묶고 상위/하위 관계를 만든다.
5. **속성 정의**: 클래스 간 관계(Object Property)와 값(DataType Property)을 정의한다.
6. **속성 제약 정의**: Domain, Range, 개수 제한 같은 제약을 건다.
7. **인스턴스 생성**: 실제 개체를 만든다.

구축에는 두 가지 역량이 모두 필요하다.

- **도메인 전문 지식**: 그 분야의 개념과 용어, 규칙을 아는 사람
- **온톨로지에 대한 기술적 이해**: 이를 형식으로 옮길 줄 아는 사람

접근 방식은 두 가지다.

- **탑다운**: 도메인 전문가가 개념 체계를 먼저 설계하고 데이터를 맞춘다.
- **바텀업**: 가지고 있는 데이터를 분석해서 스키마를 도출한다.

실무에서는 둘을 섞어서 쓴다.

### 7. CQ(Competency Question, 적격질의)

모델링에서 가장 중요한 도구가 **CQ**다. CQ는 **이 온톨로지가 답할 수 있어야 하는 질문의 목록**이다. 세 가지 역할을 한다.

- **범위를 정한다**: CQ에 없는 것은 모델링하지 않는다. 범위가 무한정 커지는 것을 막는다.
- **설계 기준이 된다**: 질문에 필요한 클래스와 관계가 곧 모델의 요구사항이다.
- **완료를 검증한다**: 모델을 만든 뒤 CQ를 실제 쿼리로 바꿔 실행해서 답이 나오면 완료, 안 나오면 모델에 빠진 것이 있다는 뜻이다.

**CQ에서 모델을 만드는 4단계**

1. **질문 쓰기**: 도메인 사용자가 실제로 궁금해할 질문을 자연어로 쓴다. 예: "불합격 판정을 받은 장비는 무엇인가?"
2. **단어 뽑기**: 질문에서 **명사는 클래스 후보**, **동사는 관계 후보**로 뽑는다. 위 질문에서는 `판정`, `장비`가 클래스 후보이고 `받다`가 관계 후보다.
3. **모델 그리기**: 뽑은 단어를 클래스와 관계로 그린다. `장비 - 판정을 받는다 - 판정`
4. **되묻기**: 그린 모델로 질문에 답할 수 있는지 다시 확인하고, 안 되면 보완한다.

**예: 수요예측에 쓰는 온톨로지**
- 날씨, 공급사, 재고 같은 수요예측에 영향을 주는 요소를 다룬다.
- 이 경우 CQ는 "이 제품의 수요에 영향을 주는 날씨 조건은 무엇인가?", "이 제품을 공급하는 공급사와 납기는?"처럼 **수요예측에 필요한 데이터를 찾아낼 수 있는 질문**이 된다.
- 즉 온톨로지가 수요를 직접 예측하는 것이 아니라, **예측에 필요한 데이터를 연결해서 결과로 내놓을 수 있어야 한다**는 뜻으로 이해했다. 실제 예측 계산은 별도 모델이 한다. (이 해석은 확인이 필요하다.)

### 8. 행동은 어떻게 표현하는가

온톨로지는 "무엇이 있고 어떻게 연결되는가"를 정의하는 데 강하고, Java 메서드처럼 실행 코드를 담는 데는 맞지 않는다. 행동은 보통 다음 방식으로 표현한다.

- **관계로 표현**: `작업자A - 검사한다 - 장비B`. 단순하지만 시간, 결과 같은 부가 정보를 붙이기 어렵다.
- **이벤트 클래스로 표현**: 행동 자체를 하나의 인스턴스로 만든다. 가장 흔한 방식이다. `검사#001`을 만들고 수행자, 대상, 일시, 결과를 속성으로 연결한다.
- **규칙으로 표현**: "불합격이면 재검사 대상이다" 같은 조건은 SWRL이나 SHACL 같은 규칙 언어로 쓴다. 실제 실행은 별도 애플리케이션이 담당한다.

### 9. 프로테제와 남은 주제

**프로테제(Protégé)** 는 스키마를 만드는 도구다. 클래스, 계층, 속성, 제약을 정의하고 인스턴스를 만들 수 있다. 시작하려면 온톨로지 전체의 ID인 **IRI**부터 정해야 한다. IRI, Domain/Range 같은 개념은 별도 글에서 다룬다.

아직 정리하지 못한 주제는 두 가지다.

- **쿼리**: RDF 계열의 질의 언어인 SPARQL로 질의한다.
- **추론**: 추론기가 규칙에서 새 사실을 도출하는 과정이다. 프로테제에서는 추론기를 플러그인 형태로 돌려서 모델의 모순을 찾거나 분류를 자동으로 얻는다.

이 두 가지는 실습하면서 이어서 정리할 예정이다.
