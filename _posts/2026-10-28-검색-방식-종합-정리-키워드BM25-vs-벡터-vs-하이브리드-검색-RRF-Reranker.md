### 들어가며

RAG를 공부하다 보면 검색 관련 용어가 한꺼번에 쏟아진다. 키워드 검색, BM25, 벡터 검색, 하이브리드 검색, RRF, Reranker까지, 각각은 따로 들어서 알겠는데 **한 줄로 이어서 설명하려면** 막힌다. 앞서 정리한 [PostgreSQL 전문 검색](/posts/PostgreSQL-전문-검색-정리-키워드-검색은-LIKE와-뭐가-다를까/)과 [임베딩 모델](/posts/임베딩-모델이란-RAG-검색이-실제로-비교하는-것/) 글이 각각 키워드 쪽, 벡터 쪽 이야기였다면, 이 글은 둘을 한 번에 비교하고 합치는 방법까지 정리한 종합편이다.

### 1. 먼저 결론

- **키워드 검색**은 검색어의 **단어가 문서에 들어 있는지**를 본다. 대표 점수 방식이 **BM25**다.
- **벡터 검색**은 질문과 문서를 **임베딩(숫자 배열)** 으로 바꿔서 **의미가 가까운지**를 본다.
- 둘은 잘하는 것이 반대라서 **하이브리드 검색**으로 결과를 합친다. 순위를 합치는 대표 방법이 **RRF**다.
- 합친 결과 상위 몇십 건을 **Reranker**로 한 번 더 정밀하게 정렬하면 품질이 올라간다.
- 전체 흐름은 `후보 넓게 찾기(키워드 + 벡터) → 순위 합치기(RRF) → 정밀 재정렬(Reranker) → LLM에 전달`이다.

### 2. 키워드 검색과 BM25

키워드 검색은 문서를 단어 단위로 쪼개서 **역색인(inverted index)** 에 저장한다. 역색인은 책 뒤의 "찾아보기"처럼 `단어 → 그 단어가 나오는 문서 목록`을 미리 만들어 둔 구조다. 검색어가 들어오면 문서를 처음부터 읽지 않고 이 목록만 보면 되어서 빠르다.

문제는 "맞는 문서가 여러 개일 때 어떤 것을 위에 올릴까"이고, 이 점수를 매기는 방식이 **BM25**다. 아이디어는 세 가지다.

- **TF(단어 빈도)**: 검색어가 문서에 많이 나올수록 점수가 높다. 단, 많이 나와도 **점수는 점점 완만하게만** 오른다(포화).
- **IDF(역문서 빈도)**: 전체 문서에서 **드물게 나오는 단어**일수록 점수가 높다. `the`처럼 어디에나 있는 단어는 거의 도움이 안 되고, 희귀한 용어가 나오면 큰 단서다.
- **문서 길이 보정**: 같은 횟수로 나와도 **짧은 문서**가 더 관련 있다고 본다. 긴 문서는 단어가 우연히 많이 나오기 쉽기 때문이다.

식으로 쓰면 다음과 같다. 외울 필요는 없고 위 세 가지가 어디에 들어가는지만 보면 된다.

```text
score(q, d) = Σ  IDF(t) × f(t,d) × (k1 + 1) / ( f(t,d) + k1 × (1 − b + b × |d| / avgdl) )
              t∈q
```

- **f(t,d)**: 단어 t가 문서 d에 나온 횟수(TF)
- **|d| / avgdl**: 문서 길이를 전체 평균 길이로 나눈 값(길이 보정)
- **k1**: TF 포화 정도를 정하는 값. 클수록 많이 나온 문서를 더 우대한다. 흔히 1.2 근처를 기본으로 쓴다.
- **b**: 길이 보정의 세기. 0이면 길이를 무시하고 1이면 완전히 반영한다. 흔히 0.75를 기본으로 쓴다.

PostgreSQL의 `ts_rank`와 비교하면 차이가 보인다. `ts_rank`는 기본적으로 **출현 횟수만** 보고 **단어의 희귀성(IDF)** 을 모른다. BM25는 IDF와 길이 보정까지 반영하기 때문에 키워드 검색 엔진(Elasticsearch, OpenSearch 등)의 기본 점수 방식으로 널리 쓰인다.

#### 키워드 검색의 강점과 한계

- **강점**: 정확한 용어, 제품명, 에러 코드, 고유명사, 약어를 잘 찾는다. 어떤 단어가 맞았는지 보이므로 결과를 설명하기 쉽다. 비용이 낮고 빠르다.
- **한계**: 동의어와 의미를 모른다. `자동차`로 검색하면 `차량`만 있는 문서는 못 찾는다. 질문을 문장으로 길게 쓰면 문서와 겹치는 단어가 없어서 놓치기도 한다.
- **한국어**는 조사와 어미가 붙기 때문에 단어를 제대로 쪼개는 **형태소 분석기(nori 등)** 설정이 검색 품질을 좌우한다.

### 3. 벡터 검색

벡터 검색은 문서를 미리 임베딩해서 저장해 두고, 검색할 때 질문도 **같은 모델**로 임베딩해서 **거리가 가까운 순**으로 가져온다. 자세한 원리는 [임베딩 모델 글](/posts/임베딩-모델이란-RAG-검색이-실제로-비교하는-것/)에 정리했고, 여기서는 키워드 검색과 비교되는 점만 짚는다.

- **강점**: `자동차`와 `차량`, `happy`와 `joyful`처럼 **표현이 달라도 뜻이 비슷하면** 찾는다. 질문을 자연스러운 문장으로 써도 된다.
- **한계**: 정확한 용어나 코드, 숫자, 고유명사에는 약할 수 있다. `ERR-4021` 같은 에러 코드는 의미가 없는 문자열이라 임베딩이 비슷한 다른 코드와 섞이기도 한다. 또 왜 이 문서가 가깝다고 판단했는지 설명하기 어렵다.
- **비용**: 문서를 저장할 때, 검색할 때 모두 **임베딩 모델 호출**이 필요하다. 문서가 많으면 근사 검색 인덱스(HNSW 등)도 필요하다.
- **같은 모델 규칙**: 문서와 질문은 반드시 같은 임베딩 모델로 만들어야 한다. 모델을 바꾸면 문서를 전부 다시 임베딩해야 한다.

### 4. 키워드 vs 벡터 비교

| | 키워드 검색 (BM25) | 벡터 검색 |
|---|---|---|
| 비교하는 것 | 단어가 겹치는가 | 의미가 가까운가 |
| 저장 구조 | 역색인(단어 → 문서 목록) | 임베딩 벡터 + 근사 검색 인덱스 |
| 동의어, 다른 표현 | 못 찾음 | 찾음 |
| 정확한 용어, 코드, 고유명사 | 잘 찾음 | 놓칠 수 있음 |
| 긴 자연어 질문 | 겹치는 단어가 없으면 약함 | 강함 |
| 결과 설명 | 맞은 단어가 보임 | 설명하기 어려움 |
| 비용 | 낮음 | 임베딩 호출 + 인덱스 비용 |

예를 들어 질문이 `ERR-4021이 왜 나지?`라면 키워드가 유리하고, `서버가 갑자기 느려졌을 때 어디부터 봐야 해?`라면 벡터가 유리하다. 실제 사용자는 두 종류의 질문을 섞어서 하기 때문에 한쪽만 쓰면 반드시 놓치는 구간이 생긴다.

### 5. 하이브리드 검색

**하이브리드 검색**은 키워드 검색과 벡터 검색을 **둘 다 실행하고 결과를 합치는** 방식이다. 정확한 용어는 키워드가, 뜻이 비슷한 표현은 벡터가 메워 준다.

합칠 때 어려운 점은 **두 점수의 단위가 다르다**는 것이다. BM25 점수는 0~수십 단위로 나오고, 벡터 유사도는 0~1 사이로 나온다. 그대로 더하면 한쪽이 지배한다. 그래서 크게 두 가지 방법을 쓴다.

#### 방법 1. 점수를 정규화해서 가중합

두 점수를 같은 범위(예: 0~1)로 맞춘 뒤 비율을 정해서 더한다.

```text
최종 점수 = α × 정규화된 키워드 점수 + (1 − α) × 정규화된 벡터 점수
```

- `α`로 어느 쪽을 더 믿을지 조절할 수 있다.
- 단점은 정규화 방식(min-max 등)에 따라 결과가 흔들리고, 검색마다 점수 분포가 달라서 `α`를 잡기 까다롭다는 점이다.

#### 방법 2. 점수가 아니라 순위를 합치는 RRF

**RRF(Reciprocal Rank Fusion)** 는 점수를 버리고 **순위만** 사용한다. 각 검색 결과 목록에서 문서의 순위를 구하고 다음처럼 더한다.

```text
RRF 점수(d) = Σ  1 / (k + rank_i(d))
              i
```

- `rank_i(d)`는 i번째 검색 결과에서 문서 d의 순위(1등이면 1)다.
- `k`는 상수이며 흔히 **60**을 쓴다. 상위권 순위 차이가 점수를 지나치게 흔들지 않게 완화하는 역할이다.
- 어느 목록에도 없는 문서는 그 항을 0으로 본다.

네 개의 문서로 계산해 보면 이렇다. 키워드 검색 순위는 A, B, C이고 벡터 검색 순위는 B, D, A라고 하자(k = 60).

| 문서 | 키워드 순위 | 벡터 순위 | RRF 점수 | 최종 순위 |
|---|---|---|---|---|
| B | 2 | 1 | 1/62 + 1/61 = 0.0325 | 1 |
| A | 1 | 3 | 1/61 + 1/63 = 0.0323 | 2 |
| D | - | 2 | 1/62 = 0.0161 | 3 |
| C | 3 | - | 1/63 = 0.0159 | 4 |

- **두 목록에 모두 상위로 올라온 B와 A**가 한쪽에만 나온 D, C보다 위에 온다. 서로 다른 방식이 함께 좋다고 한 문서를 우대하는 효과다.
- A는 키워드에서 1등이었지만 벡터에서 3등이라 B에게 밀렸다.
- 점수 단위를 맞출 필요가 없어서 구현이 간단하고, `α` 같은 튜닝 값이 거의 없다. 그래서 하이브리드의 기본값처럼 많이 쓰인다. OpenSearch, Elasticsearch 같은 검색 엔진도 하이브리드 결합 기능을 제공하며, RRF나 정규화 방식은 제품과 버전마다 지원 범위가 다르다.
- 단점은 순위만 쓰기 때문에 "1등이 압도적으로 좋은지, 간발의 차인지" 같은 **점수 차이 정보가 사라진다**는 점이다.

### 6. Reranker

하이브리드까지 하면 후보를 넓고 빠르게 모을 수 있다. 하지만 상위 결과의 **순서가 정밀하지는 않다.** 그래서 마지막에 **Reranker**로 상위 후보만 다시 정렬한다.

앞의 검색 방식들과 구조가 다르다.

- **임베딩 검색(Bi-encoder)**: 질문과 문서를 **각각 따로** 벡터로 바꾸고 거리를 잰다. 문서 벡터를 미리 계산해 둘 수 있어서 **수백만 건에서도 빠르다.** 대신 질문과 문서가 서로를 보지 못한 채 압축되므로 정밀도에 한계가 있다.
- **Reranker(Cross-encoder)**: 질문과 문서를 **한 쌍으로 함께** 모델에 넣어서 관련도 점수를 직접 낸다. 질문과 문서 사이의 세밀한 관계를 볼 수 있어서 **정확하다.** 대신 질문마다 후보 하나하나를 모델에 통과시켜야 해서 **느리고 비싸다.** 그래서 전체 문서가 아니라 상위 수십 건에만 적용한다.

그래서 2단계로 나눠서 쓴다.

1. **1단계 검색(Retrieval)**: 키워드 + 벡터 + RRF로 후보 50~100건을 빠르게 모은다. 목표는 **놓치지 않는 것(재현율)** 이다.
2. **2단계 재정렬(Reranking)**: Reranker로 그 후보를 정밀하게 다시 정렬하고 상위 3~5건만 LLM에 준다. 목표는 **위쪽을 정확하게 만드는 것(정밀도)** 이다.

LLM의 컨텍스트에 넣을 수 있는 양은 한정되어 있고 관련 없는 문서가 섞이면 답변 품질이 떨어지므로, 마지막에 상위 소수만 정확히 뽑아 주는 이 단계가 RAG 품질에 크게 기여한다.

### 7. 전체 파이프라인 정리

```text
사용자 질문
   ├─→ 키워드 검색 (BM25)  ─→ 후보 목록 1
   └─→ 벡터 검색 (임베딩)   ─→ 후보 목록 2
              ↓
       순위 합치기 (RRF) → 후보 50~100건
              ↓
       Reranker (Cross-encoder) → 상위 3~5건
              ↓
       LLM에 컨텍스트로 전달 → 답변 생성
```

| 단계 | 하는 일 | 속도 | 정밀도 | 목표 |
|---|---|---|---|---|
| 키워드 (BM25) | 단어 일치로 후보 찾기 | 매우 빠름 | 보통 | 용어를 놓치지 않기 |
| 벡터 | 의미 유사도로 후보 찾기 | 빠름 | 보통 | 표현이 달라도 찾기 |
| RRF | 두 목록의 순위 합치기 | 매우 빠름 | - | 두 방식의 장점 결합 |
| Reranker | 질문-문서 쌍을 정밀 평가 | 느림 | 높음 | 상위 결과 품질 |

### 8. 상황별로 무엇을 쓸까

- **용어, 코드, 제품명 검색이 대부분**이면 키워드(BM25)만으로도 충분하다. 단순하고 설명 가능하다.
- **자연어 질문에 답하는 RAG**라면 벡터 검색이 기본이고, 정확한 용어 질문이 섞이면 하이브리드를 고려한다.
- **품질이 중요한데 답변이 어긋난다**면 하이브리드 위에 Reranker를 얹는 것이 흔한 다음 단계다.
- 처음부터 모든 것을 갖출 필요는 없다. **키워드 → 벡터 → 하이브리드(RRF) → Reranker** 순서로, 부족함이 확인될 때 하나씩 얹는 편이 비용 면에서도 낫다.
- 어느 구성이 좋은지는 데이터와 질문 유형마다 다르므로, 실제 질문 샘플로 직접 비교해서 정하는 것이 맞다.

### 정리

- **키워드 검색**은 단어 일치를 본다. BM25는 TF(빈도, 완만하게 포화), IDF(희귀 단어 가중), 문서 길이 보정으로 점수를 매긴다.
- **벡터 검색**은 임베딩 거리로 의미 유사도를 본다. 동의어에 강하지만 정확한 용어, 코드에는 약할 수 있다.
- **하이브리드 검색**은 둘을 합친다. 점수 단위가 달라서 정규화 가중합을 쓰거나, 순위만 합치는 **RRF**(`1 / (k + 순위)`의 합, 보통 k = 60)를 쓴다.
- **Reranker**는 질문과 문서를 쌍으로 넣어 정밀하게 재정렬한다. 느려서 상위 후보에만 적용한다.
- 흐름은 `넓게 모으기(키워드 + 벡터) → RRF → Reranker → LLM`이다. 앞 단계는 놓치지 않는 것, 뒤 단계는 정확하게 고르는 것이 목표다.
